# 设计 2/3：分级 / 静默 / 节流策略模型

> 上游设计：`2026-09-08-wechat-task-reminder.md`（§5.3）
> 本文档据 **2026-09-09 真机限流实测**修订了原设计的节流模型（见 §4）
> 定稿日期：2026-09-09

---

## 1. 配置模型（可覆盖，默认值即已定方案）

```ts
interface ReminderPolicy {
  enabled: boolean                  // 总开关，默认 false（微信提醒是可选增量）
  immediatePriorities: string[]     // 默认 ['p0','p1'] —— 到期立即推
  digestPriorities: string[]        // 默认 ['p2','p3'] —— 并入每日汇总
  digestAt: string                  // 'HH:mm'，默认 '09:00'
  quietHours: { start: string; end: string } | null   // 默认 { start:'22:00', end:'08:00' }
  quietHoursBypassPriorities: string[]                // 默认 ['p0'] —— P0 穿透静默
  hourlyLimit: number               // 默认 6
  dailyLimit: number                // 默认 50
  catchupWindowHours: number        // 默认 24
  catchupMaxItems: number           // 默认 10（合并成一条摘要的条目上限）
  breakerCooldownMinutes: number    // 默认 30
  channel: 'auto' | 'wechat' | 'browser'  // 默认 'auto'
}
```

存放位置：`meta` 表 `reminder_policy`（JSON），与现有 `ai_default_workspace` 等设置同机制，**不新建表**。

**任务级覆盖**：任务 `extra.reminderPolicy` 可覆盖 `enabled` / `immediatePriorities` 判定（只允许"更保守"，不允许放宽到超过全局限额）。

## 2. 分级与静默的判定顺序

对每条到期提醒，按顺序判定：

```
1. 全局 enabled = false                → 不推（前端行为不变）
2. 任务已 done/cancelled/archived      → 不推
3. fired_at 非空                       → 不推（幂等，见设计 3）
4. 是否在静默时段？
     ├─ 是，且优先级 ∈ quietHoursBypassPriorities（默认 P0） → 允许即时推
     └─ 是，其他优先级                                     → 转入次日汇总队列
5. 优先级 ∈ immediatePriorities？      → 即时推
   否则                                → 转入当日/次日汇总
6. 节流判定（§3/§4）                   → 通过则发，否则入队
```

**关键口径**（原设计未写死的两处，此处定死）：

| 问题 | 定稿 |
|---|---|
| 静默期内 P0 是否推 | **推**。P0 是"必须立刻知道"，静默只约束 P1/P2/P3 |
| 静默期内 P1 是否推 | 不推，并入次日汇总 |
| 静默期跨日 | `start > end` 视为跨午夜（22:00–08:00 表示当天 22:00 到次日 08:00）；`start === end` 视为不启用 |
| 汇总条数 | 单条摘要最多列 `catchupMaxItems`（默认 10）条，超出写"…等 N 条"，不逐条刷屏 |

## 3. 软预算层（保留原设计）

| 项 | 默认 | 说明 |
|---|---|---|
| 每小时上限 | 6 | 抄 lanbaolu 实测值 |
| 每日上限 | 50 | 同上 |
| 超限行为 | **入队**，不丢 | 但**出队时必须合并**（见 §4） |

预算按「已成功发送 + 已尝试发送」计数，窗口为滑动小时/自然日。

## 4. 熔断层（本次实测新增，原设计缺失）

### 4.1 为什么必须有

2026-09-09 真机实测：

| 观察 | 数值 |
|---|---|
| 连发触发拒发的条数 | 12 秒内 11 条，**前 9 条成功、第 10 条起被拒** |
| 被拒后静置 5 分钟 | **仍被拒**（未自动恢复） |
| 恢复方式 | **接收者给机器人发一条消息** → 立即恢复（301ms 成功） |
| 被拒时 token / 健康状态 | `contextToken=yes`、`health=healthy` → 不是会话过期，是**账号级发送限制** |

**推论**：原设计"超限进队列延迟发送"会在额度恢复时集中放出一批消息，**再次撞墙**，且用户收到一批延迟的重复提醒。

### 4.2 熔断状态机

```
CLOSED（正常）
  │  收到 delivery-failed / 连续 2 次 failed
  ▼
OPEN（熔断，默认 30 分钟）
  │  期间所有 send 直接返回 throttled，不发网络请求
  │  队列不释放，改为"合并待发"
  ▼
HALF_OPEN（冷却结束后，或探测到恢复信号）
  │  只允许发 1 条探测消息
  ├─ 成功 → CLOSED，并释放合并队列（合成一条）
  └─ 失败 → 回到 OPEN，冷却时间翻倍（上限 4 小时）
```

**恢复信号（优先于冷却计时）**：若观察到 dsh-im 侧收到过新的用户消息（`connection.status().bots[].stats.messagesReceived` 增长），视为账号发送能力已恢复 → 直接进入 HALF_OPEN 试探。这直接对应实测到的官方恢复路径。

### 4.3 队列释放规则（关键）

- 熔断/预算解除后**不逐条发送**：把队列里同优先级的条目**合并成一条摘要**再发（`catchupMaxItems` 上限）；
- 合并后原队列行删除，只留一条摘要行（或直接发完删除）；
- 若合并摘要本身发送失败 → 摘要行保留，退避重试。

---

## 5. 每日汇总

- 到 `digestAt`（默认 09:00）时，把 `digestPriorities` 内、当天（含昨夜静默期积压）到期的提醒合并成一条；
- 汇总消息格式：

```
【工作台 · 今日待办提醒】
1. 跟客户 A 开会（今天 14:00）
2. 提交周报（今天 18:00）
…等 12 条
```

- 汇总同样受预算与熔断约束；静默期内的汇总顺延到 `digestAt`。

---

## 6. 配置读取与并发

- 策略配置读一次缓存，PATCH 设置后失效重读；
- 扫描器单次扫描**可重入保护**（`scanning` 标志），避免 30s 定时器叠加；
- 所有写库操作用事务；`fired_at` 只在"已交付或已入队"后写（见设计 3）。

---

## 7. 验收标准

1. `enabled=false` 时行为与今天完全一致（不推微信、前端横幅照旧）；
2. P0 在静默时段仍即时推；P1 在静默时段不入队即时推；
3. 每小时第 7 条进入队列而非发送；
4. 收到 `delivery-failed` 后，下一次发送**不发网络请求**（直接 `throttled`）；
5. 熔断冷却结束后只发 1 条探测消息；
6. 队列释放时多条合并为一条（不是逐条放）。
