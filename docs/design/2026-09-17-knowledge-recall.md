# 知识库被会话 AI 自动调用（v1.15.3）

> 对应任务 `4be909c2-926d-4f5f-a48d-cd22cd5ec78a`。
> 相关实现：`src/shared/knowledgeRecall.ts`（纯判定）、`src/knowledge-recall.ts`（接线与状态）、
> `src/knowledge-recall-log.ts`（可观测日志）、`src/knowledge-tools.ts`（两个 Agent 工具）、
> `src/api/knowledgeRecallRoute.ts`（端点）、`SettingsModal.tsx` 的「知识库召回」分区。

## 问题

知识库有 59 条真实沉淀，但**会话 AI 不会自动用起来** —— 没人主动查就等于只是给人看的文档。

## 四个触发时机（用户确认过的）

| 时机 | 谁触发 | 证据 |
|---|---|---|
| ① 执行任务前 | `agent/session-start` → `prime()`：拿**任务标题 + 任务描述**分句检索 | 会话里出现「【工作台知识库】…」；日志 `trigger=session_start` |
| ② 遇到报错/异常 | 模型主动调 `workbench_search_knowledge`（报错原文只有它当场看得到） | 工具结果自带「关键词 / 命中条数 / 逐条相关度与依据」 |
| ③ 写码/改码前 | 同上（模块名、约定只有读代码时才确定） | 同上 |
| ④ 提交验收/复盘前 | 同上 + 回合自动召回 | 同上 |

**为什么不能只靠自动层**：自动召回只在**回合边界**拿到用户提问，
而「报错时」的原文是模型跑命令才看到的，「写码前」的关键词是读代码才确定的 ——
这两个时机自动层赶不上，必须给模型一个**当回合就能查**的入口。
反之，「开工前」和「验收前」的提问就是用户消息本身，自动层恰好覆盖。
两层合起来才是完整的（与团队记忆的 `TOOL_GUIDE` + 召回注入同构）。

## 与团队记忆（`dsh-team-memory`）对齐的行为约定

一件事不能有两套规则，所以逐条对齐，并在代码里写明出处：

| 约定 | 团队记忆 | 本实现 |
|---|---|---|
| 检索时机 | 回合收尾预取 → 下回合注入 | **不同**（v1.15.7 起改为**装配期当轮检索**，理由见「v1.15.7 的 P1」一节） |
| 零命中 | **不插占位**（保提示前缀缓存） | 同（`formatRecallText` 返回空串） |
| 琐碎消息 | 跳过但**留痕** | 同（`isTrivialQuery` + `skipped_reason` 落库） |
| 阈值方向 | 分越大越相关，`score >= minScore` | 同（但本实现是**严格大于**，理由见下） |
| 条数上限 | `maxMemories` 缺省 5 | `maxEntries` 缺省 3（知识条目带正文片段，额度更紧） |
| 可关闭 | `injectMemories=false` | 全局 + 单会话 + 环境三档 |
| 引导层 | 常量文本、讲清"何时主动查" | 同（`KNOWLEDGE_GUIDE`，order 260） |

## 打分口径（**唯一权威源**：`src/shared/knowledgeRecall.ts`）

```
hits_f   = 该字段命中的不同关键词数（f ∈ {标题, 标签, 正文}）
score_f  = weight_f * min(1, hits_f / 3) * (0.5 + 0.5 * min(1, hits_f / 关键词总数))
score    = max(标题档, 标签档, 正文档)      ← 三个字段**各自算分**，取最高（v1.15.4 修正）
  weight: 标题 0.55 / 标签 0.45 / 正文 0.25
命中判定: score > 0.34
排序: score 降序 → 本任务优先 → 更新时间降序 → id
```

**权重与覆盖率必须来自同一个字段**（v1.15.4 修）：早期写法是"权重取命中的最高一档、
覆盖率取**三字段并集**"，于是"标题碰巧共享 1 个字 + 长篇正文命中一堆"能拿到 0.5 以上，
同一篇泛化长文对任何提问都进 top-3（真实库实测 4 次提问进 3 次）。

### 这个公式是被实测逼出来的（三轮翻车记录）

1. **第一版** `weight + 0.06 * (命中词数 - 1)`：中文逐字抽词下，一篇 3000 字的条目只要正文里
   出现 8 个常见字就冲到 1.00。实测 20 字长的提问命中 3 条、**三条全是 1.00** —— 阈值与排序同时失效。
2. **第二版** `weight * (命中数/提问长度)`：又矫枉过正 —— `'盘符 根目录 文件选择'`（9 个关键词）
   查一条标题只有 6 个字的条目、命中了 5 个，仍然只有 0.31，**真实提问全被挡在门外**。
3. **第三版（现在的骨架）**：长度因子在命中 3 个词时饱和（短条目 5/6 命中≈满分，
   长正文堆 8 个字也只有 1.0），覆盖率给 50% 起步（短提问不被过度惩罚）。
4. **v1.15.4**：在第三版上加"**分字段算分**"——第三版仍把三字段并集当覆盖率的分子，
   被独立审查者用真实库抓出跨提问重复注入（见下「审查修复」第 3 条）。

### 「新旧」不进分数，只做同分排序

与团队记忆的取舍**不同**，理由写在这里：分数是给人看的"多相关"，
混进时间会让可解释的档位被污染（实测：一条 1 小时前更新的条目因此拿到刚好过线的分数，
注入了一条只靠正文里出现一个字的噪声）。时间的作用是**同分时的次序**。

### 阈值 0.34 的三条约束

1. 正文命中一律不过线（`0.25 < 0.34`，即使全覆盖）——"正文里出现关键词"不足以推送；
2. 长提问里"只碰巧共享几个字"的条目被挡下（覆盖率低 → 分数低）；
3. 真实的短提问（标题/标签命中）稳过线。

**结论：命中要落在标题或标签上，且要有一定覆盖率。** 这是知识条目质量的自然要求。

## 检索范围：本任务/本任务树优先

- 会话 → 任务的权威映射是 `task_sessions` 反查（`findTaskIdBySession`）；
- 拿不到时退到工作目录命名（`<任务ID>-<标题片段>`，`taskIdFromWorkspacePath`）**只作兜底**；
- 候选集 = 本任务链（自身 + 祖先 + 后代）在前、全库在后，按 id 去重（`candidates()`）。

## 可见性（验收第 1 条要的证据）

三处同时给，缺一不可：

1. **会话里**：`systemPrompt.context` 产出的是**持久用户角色快照**
   （`@deepseek-ai/dsh-system-prompt` 的类型注释），所以「【工作台知识库】…」会进会话记录；
2. **落库日志**：每次召回一行 `knowledge_recall_log`（关键词 / 命中 / 分数 / 依据 /
   是否注入 / 跳过原因 / 被引用），端点 `GET /api/workbench/knowledge-recall/log` 返回
   **人类可读摘要行**（不装工具也能看懂）；
3. **界面**：工作台 → 设置 → 「知识库召回」，直接列最近 30 条 + 谁被单独关掉了。

模型用到条目时调 `workbench_knowledge_recall_control(action=report_usage, entry_ids=[...])`
回填 `cited_ids`，于是"是否被引用"可判定，而不是靠猜。

## 可关闭（验收第 2 条）

| 层级 | 入口 | 语义 |
|---|---|---|
| 全局 | 设置页开关 / `POST /api/workbench/knowledge-recall/auto` | 关掉后所有会话都不自动检索与注入 |
| 单会话 | 模型 `turn_off` / `turn_on` / `clear`，或 `POST .../session` | 显式关 / 显式开（覆盖全局关）/ 回到跟随全局 |
| 配置/环境 | `Config.knowledgeRecallEnabled` | 一键降级，仍保留工具（显式查永远可用） |

**关掉 ≠ 不能查**：工具路径不经过开关（`candidates()` 与 `recallToText` 不受影响）——
这是刻意的分界，"自动打扰"与"主动检索"是两个决定。

## 噪声控制（验收第 3 条）

机制四条：
1. 阈值 0.34（正文命中不过线）+ 长度因子饱和（长正文堆字不加分）；
2. 单回合上限 3 条；
3. **单会话去重**：注入过的条目不再重复占额度（`seenIds`），重开开关时清空；
4. 琐碎消息（"好的"/"继续"/单字）跳过检索，零命中不插占位。

实测（`node scripts/repro/demo-knowledge-recall.mjs`，真实库副本 59 条）：

| 诱饵类型 | 构造 | 实测结果 |
|---|---|---|
| A 字面共享 | 换掉提问里的一个字 | 命中最多少于真实提问（逐字检索的固有边界，如实记录） |
| B 完全无关 | 关键词全是**库外汉字**（算出来的：标题/正文/标签都不出现） | **零命中**（候选池匹配 0） |
| C 跨提问重复 | 四时机的 4 句不同提问 | **无条目进 ≥3 次 top-3**（v1.15.4 补；上一版这里会炸：某长文进 3 次） |
| 批量短提问 | 5 条 | 平均 0.80 条/问，3 条零命中 |

## 已知局限（不藏着）

1. **逐字匹配，没有语义**：换一个字的提问（"方问图"）仍可能命中"方向图"的条目 ——
   这是词法检索的固有边界，脚本里如实记录，没有假装解决。要真解决需要本地向量模型，
   不是这一版的范围。
2. **单关键词查询基本不可用**：长度因子只有 1/3，任何字段的单命中都够不到阈值
   （标题 0.183 / 标签 0.15 / 正文 0.083）。口径是"提问要落在标题/标签上，或给出几个具体词"。
3. **DB 只能向前**：迁移 17 加了 `knowledge_recall_log` 表，重启后 schema 15/16 → 17。
   库比插件新时走既有的 `applyDegraded()` 降级路径（照常告警，功能不可用）。
4. **注入作用域 = 全部顶层会话**：`agent/turn-stopping` 的预取不检查会话是否关联了工作台任务，
   所以本机任何顶层会话（包括别的项目）从第 2 回合起都会拿提问去检索知识库。
   这符合"再扩到全局"的要求，但**影响面是全局的**；嫌吵可以用全局开关或单会话 `turn_off`。
5. **审查的原始凭据在本机 `_local-archive/knowledge-recall-review/`**（审查者报告、探针输出、审查者脚本）：
   按本仓约定**不入库**（`.gitignore` 已忽略 `.review-evidence/`）；**可重跑的那一份**已入库到
   `scripts/repro/knowledge-recall/`，本节引用的路径以那份为准。

## v1.15.5：用户实测抓到的两处「承诺与能力不一致」

两处都不是判定错了，而是**界面/文档说的话与实现做的事不一样** ——
这类偏差最容易被"跑起来看着正常"掩盖，所以两条都按"先红后绿 + 变异守卫"补。

### ① 「按 id 再查一次」是句假话（消费环节缺一条路）

注入文本原先写着"需要展开某条时用返回里的 id 再查一次"，而
`workbench_search_knowledge` **只会把 query 当关键词抽词打分** —— 传 uuid 必然零命中
（用户 2026-09-17 实测：`query="7532f45e-cb93-…"` → 零命中）。
后果不只是那句提示错：**52 条带 `file_link` 的镜像型条目在会话里只剩 160 字摘要**，
知识库"检索得回来、消费不下去"。

修法：

| 决定 | 理由 |
|---|---|
| 新增 `unwrapEntryId` / `isEntryIdQuery` / `findEntryById`（`knowledge-recall.ts`） | 判定与解包**只有一处实现**；工具、日志、测试共用 |
| 只认**完整 uuid**（容忍 `[id]` / `【id】` / `entry_id:` 包裹），**不做前缀模糊匹配** | 前缀会引入"两三条都匹配 → 挑哪条"，而静默挑一条正是本仓禁止的（挑错等于把另一条知识当事实塞进上下文） |
| 未知 id 当场说"没有这条知识条目"，并**照样落一行日志** | 与"零命中"分开：一个是没有这条，一个是有关键词但没过阈值 |
| id 路径放在 `task_id` 校验**之前** | id 全局唯一，取一条知识与"哪个任务"无关；先校验会把这条路无谓绑死在任务范围上 |
| `getKnowledge` 直读（不走候选缓存） | 刚从待确认里确认的条目也必须能立刻读到，不该等 15 秒 TTL |

### ② 「相关度 0.41」看着很低 —— 其实两边分母不同

团队记忆显示的是 `rawScore / (1 + rawScore)`（rawScore 无上界：标题+正文各中一次就是 4 分），
所以它的数字天然挤在 0.8~0.99；本仓显示的是**有界**权重分，上限正好是标题权重 0.55。
用户合理地问"是不是打分有问题"，实际是**刻度**问题。

修法：**内部判定与展示分离**。

```
score     = weight × min(1, hits/3) × (0.5 + 0.5×coverage)   ← 判定/排序/阈值仍用它（上限 0.55）
relevance = score / 0.55 ∈ (0, 1]                            ← 注入文本/工具/日志/界面 一律用它
```

- 选线性归一化而不是照抄 `x/(1+x)`：前者**单调**（排序与阈值行为一字不变）、**可解释**
  （0.82 就是标签档满分、0.45 就是只有正文命中），也不是渐近线（1.00 是真满分）；
- `RECALL_DEFAULTS.minScore` 仍是 0.34 **原始分**；界面口径下过线 ≈ **0.62**
  （`formatRelevance(RECALL_DEFAULTS.minScore)`）；
- 工具参数 `min_score` 改吃**归一化口径**（模型看着输出里的数字填），内部换算一次 ——
  刻意与插件 config 的原始分口径分开，并在 `src/index.ts` 注释里写明各自是哪把尺子；
- 日志表 `hits_json`：`score` 存归一化值、另存 `rawScore` 便于复算。
  **2026-09-17 之前的旧行只有 `score`（当时是原始分）**，会显得偏小 —— 已知局限，不回溯改。

### 最终方案：闸门不降，差一点点的给**一行提示**

```
score > 0.34        → 完整块注入（摘要 + 文档路径 + 两条纪律，实测约 1000 字符）
0.20 < score ≤ 0.34 → 一行提示（id + 标题 + 相关度，实测约 90 字符）—— 明说"未达注入闸门、仅供参考"
score ≤ 0.20        → 什么都不插（不占位）
```

- `hintScore = 0.20` **是量出来的**：11 条真实提问里正确答案的最低分是 0.275，而唯一一条
  "库里真没有对应条目"的提问只有 0.052 —— 两者之间有 0.22 的空档，0.20 落在空档里。
- 提示**看起来就不像已确认的知识**（不给摘要、不给分类、自报"未达闸门"），
  这样模型会把它当线索、而不是当事实。
- 提示也守**会话去重**（`hintedIds`，与 `seenIds` **分开**：提示过的条目将来真命中了
  仍然要能被完整注入，不能被永久压制）和**单回合上限**（`maxHints = 2`）。
- `willInject()` 把"有提示"也算进"会在会话里留下东西"，否则日志会写"没注入"而会话里明明有一行。

### P1 检索时机重构 —— 治「静默漏检索」

**现象（用户实测抓到）**：用户问「团队记忆系统项目过程中的阶段有什么可以改进的地方？」，
库里已有一条高度相关的《复盘：团队记忆系统落地搭建…》（`8aaf98bd`，09:58:55Z 入库），
自动层**一声没吭**。

**根因（定位到具体回合，不是打分问题）**：turn 16 那一轮里有**两条用户本人消息** ——
实质提问（10:05:40）+「停」（10:06:37）。回合收尾钩子只取 `latestUserMessage` = **最后一条**，
而「停」被 `isTrivialQuery` 判为琐碎 → **直接跳过检索**，那句实质提问**从未被检索过**。
复算：该条目对那句提问得 0.397（相关度 0.72），本应走完整块注入 ——
**失败发生在打分之前**，所以提示档也救不了它。落库只剩
`#30 10:06:40 [turn] injected=0 matched=0 「停」`，一个字都没提那句提问（**静默丢件**）。

**更深一层：时机本身就抄错了**。现行"回合收尾预取 → 下回合注入"是从团队记忆照搬的形状，
而团队记忆延后的前提是**它的检索要出网**（云端优先 + 本地兜底、5s 超时、fire-and-forget），
放进提示装配的关键路径不合适。**本仓的检索是本地 SQLite + 纯打分（毫秒级）—— 那个前提不成立。**
代价实测三条：①知识晚一轮到（问问题那一轮永远看不到）；②话题一换就错位（注入的是"上一件事"的知识）；
③一轮多条用户消息时前一条被静默丢掉（上面那个 bug 就是它的症状）。

**修法**：

| 决定 | 理由 |
|---|---|
| 检索移进 `systemPrompt.context`（`manager.assemblyInjection`） | 装配期用户消息已经在会话事件里（顺序是 `turn/start` → `user/message` → `request/header`），成本是一次本地查询 |
| 取词范围 = **本回合全部**用户本人消息（`currentTurnUserMessages`），逐句检索后合并 | 只取最后一条 = 上面那次事故；逐句检索保证"每条用户消息都有交代、都有日志行" |
| 装配键 `assemblyKey = turn + 本回合消息原文` | 同键直接复用 `cachedText`：同回合文本稳定（保前缀缓存），且"装配多次只算一次检索"（账不被装配次数放大） |
| **本回合还没有用户消息时不写终态键** | 否则消息到达后这一回合再也不会被检索 —— 正好复现要修的那个 bug（这条是写实现时发现的第二个坑，有单测钉） |
| `agent/turn-stopping` 只留两件事：补做开工前（F5）+ 观测 | 不再做回合检索；观测见下 |
| `prime` 不再写 `pendingText`，改挂 `primeOutcome`，装配期与当轮结果**合并** | 实测 turn 15 算出的结果（`#27 matched=61`）被 10:04:33 的 `session_start` prime（`#29`）**覆盖** → 从未送达 |
| `noteUnretrieved`：有用户消息但装配期没检索 → 落一行 `turn` 日志（`skipped_reason`） | "该做的事没做、账上看不出来"是本仓最忌讳的一类；宁可噪声也不能让丢失在账上消失 |

**附带收益（正是验收要求本身）**：四时机里的「报错时 / 写码前」从"只能靠工具"变成自动层也能接住
—— 报错原文与模块名现在出现在用户消息里就会被当轮检索。

**守卫**（`test/knowledgeRecallWiring.test.mjs`，全部用真实 `SessionEvent` 形状、先红后绿）：

| 测试 | 装回缺陷后变红的变异 |
|---|---|

| 本回合两条用户消息（提问 + 「停」）两条都有交代 | M28 退回"只取最后一条" |

### P1b IDF 打分重构 —— 治「语义召不回」

**为什么不是"再调调分母"**：v1.15.6 的两个变体都被实测否掉（详见上文"试过、被实测否掉的两个变体"）。
它们的失败指出同一件事：**"命中几个词"不是信息量** —— 中文逐字抽词下
试/测/知/识/库/一 这类字与"盘符""时序"**等权**。

**新口径**（`src/shared/knowledgeRecall.ts` 文件头是唯一权威源）：

```
idf(t)     = ln(1 + N/df(t)) / ln(1 + N)      ∈ (0,1]   N=语料条数，df=含该词的条数（标题∪标签∪正文）
massHit_f  = Σ idf(t)，t ∈ 该字段命中的词
massQuery  = Σ idf(t)，t ∈ 语料里存在的查询词
strength_f = min(1, massHit_f / massSat)          ← 替代 min(1, 命中词数/3)
coverage_f = min(1, massHit_f / massQuery)        ← 替代 命中词数/总词数
score_f    = weight_f × strength_f × (0.5 + 0.5×coverage_f)
```

三处**刻意的取舍**：

1. **除以 `ln(1+N)` 做归一化**：裸的 `ln(1+N/df)` 量纲随库大小漂移（3 条小库任何词都只有 `ln4`，
   60 条真实库稀有词能到 `ln61`），而 `massSat` 是一个常量 —— 不归一化就会出现
   "同一份代码小库上什么都不注入、大库上什么都注入"。归一化后 `1.0` 恒定表示
   "命中了只出现在 1 条里的词"。
2. **df 按整条（标题∪标签∪正文）统计**：只看标题会让「一」这种"标题里稀有、正文里遍地"的字
   看起来很有信息量（实测标题 df=1 → idf 灌满 → 假信号）。
3. **覆盖率的分母属于"问题"、不属于字段**（三档共用），分子仍各字段自算 ——
   v1.15.4 那条"权重与覆盖率必须来自同一个字段"的修复没有被推翻。

**阈值重新标定（不是降闸门）**：`0.34` 是**旧公式**下算出来的；换了尺子必须重新刻度。
`scripts/repro/calibrate-idf.mjs` 在本机真实库（61 条）+ 本会话 12 条真实提问上扫了两维：

| 配置 | 真实完整注入 | 有可见内容 | 关键词式对照 | A/B/C 诱饵 |
|---|---|---|---|---|
| 旧公式 + 0.34（基线） | 3/12 | 11/12 | 4/4 | 全过 |
| IDF + 0.34 | 3/12 | 12/12 | 4/4 | 全过 |
| **IDF + massSat 0.6 + 0.33（选定）** | **5/12** | **12/12** | **4/4** | **全过** |
| IDF + 0.32 | 7/12 | 12/12 | 4/4 | 全过，但**P1 那条历史噪声哨兵（0.322）会被放进来** |
| IDF + 0.30 | 11/12 | 12/12 | 4/4 | 同上，且含"库里确实没有"的长 paste |

多出来的两条是**正确答案**（genui 渲染失败 0.339 →「【修正】dsh-ui 围栏整块降级」；
相关度疑问 0.334 →「复盘：团队记忆系统落地搭建」），而 `0.32` 那条闲聊
（top-1「AIAgent的Skill使用方法」）**仍被挡在门外** —— 所以停在 `0.33`。
顺带一个可观测的改善：那条闲聊的 top-1 从泛化的「安装误差补偿…（01 天线测试业务知识库）」
（旧 0.338）换成了真正相关的「AIAgent的Skill使用方法」，泛化条目掉到第二位（0.286）。

**顺带的诚实结论**：单关键词查询的口径变了。旧口径下"命中 1 个词"的长度因子只有 1/3，
所以任何单关键词都过不了线；新口径下**一个只出现在 1 条条目里的词**（idf=1）强度直接饱和 →
单关键词能命中。这是 IDF 的必然结果，也是想要的（稀有词本身就是强信号）；
而**笼统**的单关键词仍然不行（实测「条」在 41 条语料里 idf≈0.19 → 0.17 分，连提示档都够不到），
这条也有单测守着。

### P2 取代 / 过期语义

字段 `supersededById` / `validUntil`（迁移 18），召回时**压制**被取代与已过期的条目
（`isSuperseded`，纯函数、唯一实现），并单独记账 `droppedAsSuperseded`
（不并进 `droppedByScore`："分数不够"与"这条已经不作数了"是两个原因）。

- 为什么是**压制**而不是降权：一条被明确标注"已被 X 取代"的知识，只要还能进上下文，
  模型就有机会把作废的结论当事实用；分数高低不改变这一点。
- 按 id 直读**仍然能取到**（那是显式动作），但回执必须标注
  "⚠️ 本条已被 [X] 取代 / 已过期" —— 否则作废结论会被当成事实用。
- API：`PATCH /api/workbench/knowledge/:id` 支持这两个字段；指向不存在的 id、
  指向自己、时间串不可解析 —— 一律**当场 400**（不静默接受，否则"已被 X 取代"是句查不到出处的话，
  而压制照样生效）。
- 工具：关键词零命中时会补一句"另有 N 条已被取代/已过期，未参与检索"。

### P3 减少两步消费

98% 的条目正文 > 160 字（平均 1671 字）。`RECALL_DEFAULTS.topSnippetLength = 400`：
**top-1** 的摘要放宽到约 400 字（其余仍 160），走同一个 `buildSnippet`（位置取法不变，
只是长度不同）。成本见上表（每次注入 +230~241 字），收益是"最相关的那条"通常一次就能读完
背景 + 结论，不必再调一次工具（少一步）。

### P4 引用回报自动化

`cited_ids` 原先只靠模型自觉调 `report_usage`（实测经常会忘）。现在回合收尾自动判定：
**这一回合刚注入过**的条目，其 id 或**标题前 12 字**出现在模型这一回合的
`assistant/message` 里 → 自动标 `cited`。

三条边界（都为了"宁可漏标、不可瞎标"）：

1. **只判本回合注入的条目**（`deliveredTurn === 当前回合`）—— 不给历史注入翻旧账；
2. **提示行注入的不算**（提示是"仅供参考"，顺着它去查 ≠ 引用它）；
3. **只读 `assistant/message`** —— 插件注入的 `user/message` 快照里就抄着知识块标题，
   拿它当"模型引用了"会让自动判定变成自激（注入什么就自动标成引用了什么）。

### P5 「该查未查」先只观测

用户话里带报错特征词（`looksLikeErrorReport`，判据故意宽）而这一回合模型没调用过检索工具
→ 落一行 `suggested_miss`。**只观测、不强制**（不替模型做决定，不引入新行为风险），
但必须**落库**：插件自己的可读日志在本机没落盘（`dsh-web.log` 是 0 字节），
只打 console 等于没有证据。

### 收尾② 那条"用正文打补丁"的条目 —— **结论是无需动作**（如实记）

`scripts/repro/find-supersede-candidates.mjs` 在真库（61 条）上只找到两条候选：
`8aaf98bd` 是正文里出现"作废"一词的**误报**；
`e140bb1c`（【修正】dsh-ui 围栏整块降级…）才是真正的"用正文打补丁"条目 ——
它写着"本条修正已入库的**另一条**…请以本条为准"。

但那条被修正的旧条目（《…genui 只能走 DOM 通道》）**用户早已删除**（当前库里查不到）。
也就是说：**没有可供 supersede 的对象了**，P2 要结构化的那个关系已经通过删除解决。
因此这一项的动作是：

- 提供 `scripts/knowledge-supersede.mjs`（dry-run 默认 + `--apply` 强制先备份 + 复验召回）；
- **不改** `e140bb1c` 的正文 —— 那句"另一条"现在指向一个不存在的条目，
  属于历史陈述；删改用户的知识正文是**人工确认**范围内的事，不在这里静默做。

### 数据形态（不写代码，留给产品决策）

### 一处如实记录的事故（诊断脚本把线上库推高了版本）

排查"用正文打补丁的条目"时，我写的诊断脚本用了 `openWorkbenchDb()` 打开**线上库** ——
那个函数会**自动跑迁移**，于是线上库被推到 schema 18，而正在运行的插件还是 v17：
下次重启它会读到"schema 比它新"而进入降级模式。**发现即回退**
（`scripts/repro/rollback-live-schema.mjs`：备份 → 删两列与索引 → `schema_version` 改回 17 →
复验条目数与版本），线上库现为 **17 / 61 条**，与装盘版本一致。
诊断脚本已改成 `new DatabaseSync(path, { readOnly: true })`，并在注释里写明这条教训。

**教训**：`openWorkbenchDb` 是"打开即迁移"的入口，**任何只读目的都不该用它**。

### 已知局限（不藏着）

1. **取代关系没有界面**：只能走 `PATCH /api/workbench/knowledge/:id` 或
   `scripts/knowledge-supersede.mjs`。知识字段属于人工确认范围，没有做成 AI 自动写入；
   界面上的"已取代"徽标列为后续项。
2. **引用自动判定是启发式**：标题前 12 字匹配有漏标（模型改写标题前半段）与误标
   （两条同前缀标题）的可能，因此"漏标 > 误标"地偏保守，且每次标记都留日志可申诉。
3. **P3 只放宽了 top-1**：第 2、3 条仍是 160 字；真要把"两步"也消掉，得让工具在小额度下
   就能一次取到全文（那是 P3 的下一档，没做）。
4. **每个 15s 窗口多一次全库正文扫描**（IDF 的 df 统计）。实测
   （`scripts/repro/bench-idf-stats.mjs`）：真库 61 条约 **41ms**（缓存命中约 5ms），
   压测 500/2000/5000 条分别是 213/761/1921ms。它落在**装配期**（用户等待里），
   所以条数上万时必须换成"增量维护 df 或落一张 `term_stats` 表"，不能每回合重扫 ——
   那是条数上万时的事，现在没做，但数字留在这里。
5. **两个文件超出规模红线**：`src/knowledge-recall.ts` 971 → **1330 行**、
   `src/shared/knowledgeRecall.ts` 697 → **997 行**（规范目标：纯逻辑模块 ≤ 200 行）。
   本版**明确不做**拆分：这是一次改口径的版本，把"搬代码"混进来会让归因变糊
   （本仓有过"拆分后反而更大"的先例）。拆分的边界已经清楚（事件解包助手 →
   `knowledge-recall-events.ts`；打分 → `recallScoring.ts`，渲染 → `recallFormat.ts`），
   作为独立一项记在后续。
