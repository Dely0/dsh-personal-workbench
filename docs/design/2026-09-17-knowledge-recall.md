# 知识库被会话 AI 自动调用（v1.15.3）

> 对应任务 `4be909c2-926d-4f5f-a48d-cd22cd5ec78a`。
> 相关实现：`src/shared/knowledgeRecall.ts`（纯判定）、`src/knowledge-recall.ts`（接线与状态）、
> `src/knowledge-recall-log.ts`（可观测日志）、`src/knowledge-tools.ts`（两个 Agent 工具）、
> `src/api/knowledgeRecallRoute.ts`（端点）、`SettingsModal.tsx` 的「知识库召回」分区。

## 问题

知识库有 59 条真实沉淀，但**会话 AI 不会自动用起来** —— 没人主动查就等于只是给人看的文档。

## 四个触发时机（用户确认过的）

| 时机 | 谁触发 | 证据 |
|---|---|---|
| ① 执行任务前 | `agent/session-start` → `prime()`：拿**任务标题 + 任务描述**分句检索 | 会话里出现「【工作台知识库】…」；日志 `trigger=session_start` |
| ② 遇到报错/异常 | 模型主动调 `workbench_search_knowledge`（报错原文只有它当场看得到） | 工具结果自带「关键词 / 命中条数 / 逐条相关度与依据」 |
| ③ 写码/改码前 | 同上（模块名、约定只有读代码时才确定） | 同上 |
| ④ 提交验收/复盘前 | 同上 + 回合自动召回 | 同上 |

**为什么不能只靠自动层**：自动召回只在**回合边界**拿到用户提问，
而「报错时」的原文是模型跑命令才看到的，「写码前」的关键词是读代码才确定的 ——
这两个时机自动层赶不上，必须给模型一个**当回合就能查**的入口。
反之，「开工前」和「验收前」的提问就是用户消息本身，自动层恰好覆盖。
两层合起来才是完整的（与团队记忆的 `TOOL_GUIDE` + 召回注入同构）。

## 与团队记忆（`dsh-team-memory`）对齐的行为约定

一件事不能有两套规则，所以逐条对齐，并在代码里写明出处：

| 约定 | 团队记忆 | 本实现 |
|---|---|---|
| 检索时机 | 回合收尾预取 → 下回合注入 | 同（`agent/turn-stopping` → `prefetch` → `systemPrompt.context`） |
| 零命中 | **不插占位**（保提示前缀缓存） | 同（`formatRecallText` 返回空串） |
| 琐碎消息 | 跳过但**留痕** | 同（`isTrivialQuery` + `skipped_reason` 落库） |
| 阈值方向 | 分越大越相关，`score >= minScore` | 同（但本实现是**严格大于**，理由见下） |
| 条数上限 | `maxMemories` 缺省 5 | `maxEntries` 缺省 3（知识条目带正文片段，额度更紧） |
| 可关闭 | `injectMemories=false` | 全局 + 单会话 + 环境三档 |
| 引导层 | 常量文本、讲清"何时主动查" | 同（`KNOWLEDGE_GUIDE`，order 260） |

## 打分口径（**唯一权威源**：`src/shared/knowledgeRecall.ts`）

```
hits_f   = 该字段命中的不同关键词数（f ∈ {标题, 标签, 正文}）
score_f  = weight_f * min(1, hits_f / 3) * (0.5 + 0.5 * min(1, hits_f / 关键词总数))
score    = max(标题档, 标签档, 正文档)      ← 三个字段**各自算分**，取最高（v1.15.4 修正）
  weight: 标题 0.55 / 标签 0.45 / 正文 0.25
命中判定: score > 0.34
排序: score 降序 → 本任务优先 → 更新时间降序 → id
```

**权重与覆盖率必须来自同一个字段**（v1.15.4 修）：早期写法是"权重取命中的最高一档、
覆盖率取**三字段并集**"，于是"标题碰巧共享 1 个字 + 长篇正文命中一堆"能拿到 0.5 以上，
同一篇泛化长文对任何提问都进 top-3（真实库实测 4 次提问进 3 次）。

### 这个公式是被实测逼出来的（三轮翻车记录）

1. **第一版** `weight + 0.06 * (命中词数 - 1)`：中文逐字抽词下，一篇 3000 字的条目只要正文里
   出现 8 个常见字就冲到 1.00。实测 20 字长的提问命中 3 条、**三条全是 1.00** —— 阈值与排序同时失效。
2. **第二版** `weight * (命中数/提问长度)`：又矫枉过正 —— `'盘符 根目录 文件选择'`（9 个关键词）
   查一条标题只有 6 个字的条目、命中了 5 个，仍然只有 0.31，**真实提问全被挡在门外**。
3. **第三版（现在的骨架）**：长度因子在命中 3 个词时饱和（短条目 5/6 命中≈满分，
   长正文堆 8 个字也只有 1.0），覆盖率给 50% 起步（短提问不被过度惩罚）。
4. **v1.15.4**：在第三版上加"**分字段算分**"——第三版仍把三字段并集当覆盖率的分子，
   被独立审查者用真实库抓出跨提问重复注入（见下「审查修复」第 3 条）。

### 「新旧」不进分数，只做同分排序

与团队记忆的取舍**不同**，理由写在这里：分数是给人看的"多相关"，
混进时间会让可解释的档位被污染（实测：一条 1 小时前更新的条目因此拿到刚好过线的分数，
注入了一条只靠正文里出现一个字的噪声）。时间的作用是**同分时的次序**。

### 阈值 0.34 的三条约束

1. 正文命中一律不过线（`0.25 < 0.34`，即使全覆盖）——"正文里出现关键词"不足以推送；
2. 长提问里"只碰巧共享几个字"的条目被挡下（覆盖率低 → 分数低）；
3. 真实的短提问（标题/标签命中）稳过线。

**结论：命中要落在标题或标签上，且要有一定覆盖率。** 这是知识条目质量的自然要求。

## 检索范围：本任务/本任务树优先

- 会话 → 任务的权威映射是 `task_sessions` 反查（`findTaskIdBySession`）；
- 拿不到时退到工作目录命名（`<任务ID>-<标题片段>`，`taskIdFromWorkspacePath`）**只作兜底**；
- 候选集 = 本任务链（自身 + 祖先 + 后代）在前、全库在后，按 id 去重（`candidates()`）。

## 可见性（验收第 1 条要的证据）

三处同时给，缺一不可：

1. **会话里**：`systemPrompt.context` 产出的是**持久用户角色快照**
   （`@deepseek-ai/dsh-system-prompt` 的类型注释），所以「【工作台知识库】…」会进会话记录；
2. **落库日志**：每次召回一行 `knowledge_recall_log`（关键词 / 命中 / 分数 / 依据 /
   是否注入 / 跳过原因 / 被引用），端点 `GET /api/workbench/knowledge-recall/log` 返回
   **人类可读摘要行**（不装工具也能看懂）；
3. **界面**：工作台 → 设置 → 「知识库召回」，直接列最近 30 条 + 谁被单独关掉了。

模型用到条目时调 `workbench_knowledge_recall_control(action=report_usage, entry_ids=[...])`
回填 `cited_ids`，于是"是否被引用"可判定，而不是靠猜。

## 可关闭（验收第 2 条）

| 层级 | 入口 | 语义 |
|---|---|---|
| 全局 | 设置页开关 / `POST /api/workbench/knowledge-recall/auto` | 关掉后所有会话都不自动检索与注入 |
| 单会话 | 模型 `turn_off` / `turn_on` / `clear`，或 `POST .../session` | 显式关 / 显式开（覆盖全局关）/ 回到跟随全局 |
| 配置/环境 | `Config.knowledgeRecallEnabled` | 一键降级，仍保留工具（显式查永远可用） |

**关掉 ≠ 不能查**：工具路径不经过开关（`candidates()` 与 `recallToText` 不受影响）——
这是刻意的分界，"自动打扰"与"主动检索"是两个决定。

## 噪声控制（验收第 3 条）

机制四条：
1. 阈值 0.34（正文命中不过线）+ 长度因子饱和（长正文堆字不加分）；
2. 单回合上限 3 条；
3. **单会话去重**：注入过的条目不再重复占额度（`seenIds`），重开开关时清空；
4. 琐碎消息（"好的"/"继续"/单字）跳过检索，零命中不插占位。

实测（`node scripts/repro/demo-knowledge-recall.mjs`，真实库副本 59 条）：

| 诱饵类型 | 构造 | 实测结果 |
|---|---|---|
| A 字面共享 | 换掉提问里的一个字 | 命中最多少于真实提问（逐字检索的固有边界，如实记录） |
| B 完全无关 | 关键词全是**库外汉字**（算出来的：标题/正文/标签都不出现） | **零命中**（候选池匹配 0） |
| C 跨提问重复 | 四时机的 4 句不同提问 | **无条目进 ≥3 次 top-3**（v1.15.4 补；上一版这里会炸：某长文进 3 次） |
| 批量短提问 | 5 条 | 平均 0.80 条/问，3 条零命中 |

## 已知局限（不藏着）

1. **逐字匹配，没有语义**：换一个字的提问（"方问图"）仍可能命中"方向图"的条目 ——
   这是词法检索的固有边界，脚本里如实记录，没有假装解决。要真解决需要本地向量模型，
   不是这一版的范围。
2. **单关键词查询基本不可用**：长度因子只有 1/3，任何字段的单命中都够不到阈值
   （标题 0.183 / 标签 0.15 / 正文 0.083）。口径是"提问要落在标题/标签上，或给出几个具体词"。
3. **DB 只能向前**：迁移 17 加了 `knowledge_recall_log` 表，重启后 schema 15/16 → 17。
   库比插件新时走既有的 `applyDegraded()` 降级路径（照常告警，功能不可用）。
4. **注入作用域 = 全部顶层会话**：`agent/turn-stopping` 的预取不检查会话是否关联了工作台任务，
   所以本机任何顶层会话（包括别的项目）从第 2 回合起都会拿提问去检索知识库。
   这符合"再扩到全局"的要求，但**影响面是全局的**；嫌吵可以用全局开关或单会话 `turn_off`。
5. **审查的原始凭据在本机 `_local-archive/knowledge-recall-review/`**（审查者报告、探针输出、审查者脚本）：
   按本仓约定**不入库**（`.gitignore` 已忽略 `.review-evidence/`）；**可重跑的那一份**已入库到
   `scripts/repro/knowledge-recall/`，本节引用的路径以那份为准。

## v1.15.5：用户实测抓到的两处「承诺与能力不一致」

两处都不是判定错了，而是**界面/文档说的话与实现做的事不一样** ——
这类偏差最容易被"跑起来看着正常"掩盖，所以两条都按"先红后绿 + 变异守卫"补。

### ① 「按 id 再查一次」是句假话（消费环节缺一条路）

注入文本原先写着"需要展开某条时用返回里的 id 再查一次"，而
`workbench_search_knowledge` **只会把 query 当关键词抽词打分** —— 传 uuid 必然零命中
（用户 2026-09-17 实测：`query="7532f45e-cb93-…"` → 零命中）。
后果不只是那句提示错：**52 条带 `file_link` 的镜像型条目在会话里只剩 160 字摘要**，
知识库"检索得回来、消费不下去"。

修法：

| 决定 | 理由 |
|---|---|
| 新增 `unwrapEntryId` / `isEntryIdQuery` / `findEntryById`（`knowledge-recall.ts`） | 判定与解包**只有一处实现**；工具、日志、测试共用 |
| 只认**完整 uuid**（容忍 `[id]` / `【id】` / `entry_id:` 包裹），**不做前缀模糊匹配** | 前缀会引入"两三条都匹配 → 挑哪条"，而静默挑一条正是本仓禁止的（挑错等于把另一条知识当事实塞进上下文） |
| 未知 id 当场说"没有这条知识条目"，并**照样落一行日志** | 与"零命中"分开：一个是没有这条，一个是有关键词但没过阈值 |
| id 路径放在 `task_id` 校验**之前** | id 全局唯一，取一条知识与"哪个任务"无关；先校验会把这条路无谓绑死在任务范围上 |
| `getKnowledge` 直读（不走候选缓存） | 刚从待确认里确认的条目也必须能立刻读到，不该等 15 秒 TTL |

### ② 「相关度 0.41」看着很低 —— 其实两边分母不同

团队记忆显示的是 `rawScore / (1 + rawScore)`（rawScore 无上界：标题+正文各中一次就是 4 分），
所以它的数字天然挤在 0.8~0.99；本仓显示的是**有界**权重分，上限正好是标题权重 0.55。
用户合理地问"是不是打分有问题"，实际是**刻度**问题。

修法：**内部判定与展示分离**。

```
score     = weight × min(1, hits/3) × (0.5 + 0.5×coverage)   ← 判定/排序/阈值仍用它（上限 0.55）
relevance = score / 0.55 ∈ (0, 1]                            ← 注入文本/工具/日志/界面 一律用它
```

- 选线性归一化而不是照抄 `x/(1+x)`：前者**单调**（排序与阈值行为一字不变）、**可解释**
  （0.82 就是标签档满分、0.45 就是只有正文命中），也不是渐近线（1.00 是真满分）；
- `RECALL_DEFAULTS.minScore` 仍是 0.34 **原始分**；界面口径下过线 ≈ **0.62**
  （`formatRelevance(RECALL_DEFAULTS.minScore)`）；
- 工具参数 `min_score` 改吃**归一化口径**（模型看着输出里的数字填），内部换算一次 ——
  刻意与插件 config 的原始分口径分开，并在 `src/index.ts` 注释里写明各自是哪把尺子；
- 日志表 `hits_json`：`score` 存归一化值、另存 `rawScore` 便于复算。
  **2026-09-17 之前的旧行只有 `score`（当时是原始分）**，会显得偏小 —— 已知局限，不回溯改。

顺带纠错：工具描述里写的"正文命中 0.30"与代码权重 **0.25** 不一致（以代码为准改正）。

### ③ 演示脚本自身的两条缺陷（不是产品代码）

- **自动挑任务不稳**：原来取"列表里第一条带 `sourceTaskId` 的"，而 `listKnowledge` 按更新
  时间倒序 —— 知识库每新增一条就可能换任务。改为取**关联知识最多**的那个（并列按 id 定序）。

  现在 ① 的追问跑在全新会话里。
  ⚠️ 这不是放宽断言：口径仍是"该时机必须有可见命中"，改的是场景。
  判据留档：同一份代码在用户**删除条目之前**的库副本上 **15/15**、在当前库上 14/15 —— 属数据漂移。

## v1.15.6（P1）：让自动层不再"什么都不给"—— 两档闸门

### 先量化，再动手（`scripts/repro/measure-recall-rate.mjs`）

不去编查询（编出来的查询很容易被我自己优化成"刚好命中"），**直接取本会话真实发生过的
提问原文**（`knowledge_recall_log` 里 `trigger=turn` 的行，一条不改），再用一个 `minScore=0`
的管理器看"最好的候选差多远"：

| 真实提问 | top-1 | 原始分 | 阈值 |
|---|---|---|---|
| 「…genui总是渲染失败是什么问题」 | **【修正】dsh-ui 围栏整块降级**（正确答案） | 0.327 | 0.34 ❌ |
| 「…紧缩场项目（双极化馈源）…时序控制器逻辑」 | **时序控制器操作 SOP**（正确答案） | 0.309 | 0.34 ❌ |
| 「…Windows设置计划任务有哪些坑」 | **计划任务电池静默失败**（正确答案） | 0.324 | 0.34 ❌ |
| 「可以，先把skill做了。然后我们再讨论知识库功能bug」（与天线无关的闲聊） | 安装误差补偿…（泛化标题） | **0.338** | 0.34 ❌ |

**两条结论同时成立**：
1. **排序是对的** —— 三条真实提问的 top-1 全是正确答案，而且**只差 0.01~0.03**；
2. **不能靠降阈值** —— 同一批数据里一句闲聊拿 0.338，**比两个正确答案还高**，把闸门降到 0.30 就是放它进来。

基线命中率：**真实提问 1/11**（11 条里只有 1 条过线），关键词式对照 4/4。

### 试过、**被实测否掉**的两个变体（比结论更值得记）

| 变体 | 想法 | 实测结果 | 否掉的理由 |
|---|---|---|---|
| A. 覆盖率分母改成"该字段里语料存在的关键词数" | 长提问里一大半词在标题里根本不存在，不该全额进分母 | 命中率 **6/11** ↑，但 **top-1 排序被破坏** | **标签字段的分母太小**（一条只有 5~7 个标签，"语料里存在的词"往往只有三四个）→ 一个**巧合的标签命中**覆盖率被抬到 0.6+，实测「Windows设置计划任务」的 top-1 被「波控映射表规范」用标签抢走，而正确答案掉到后面 |
| B. 三个字段**共用**一个分母（只算"能进标题/标签"的词） | 分母属于"问题"，不属于字段 | 排序恢复正常，但命中率掉回 **4/11** | 分母仍被大量**无信息量的常用字**（试/测/知/识/库/一/现…）撑大 —— 它们确实"存在于某条标题或标签里"，但携带的信息接近 0 |

B 的失败指出了真正的下一步：**必须按信息量给词加权（IDF）**，而不是继续在"分母怎么算"上做文章。
那是一次更大的打分重构（会改掉文件头那张口径表与一批精确值断言），**不适合和 P1 混在一起做**，
已记进后续任务（P2–P5 那张草稿）。

### 最终方案：闸门不降，差一点点的给**一行提示**

```
score > 0.34        → 完整块注入（摘要 + 文档路径 + 两条纪律，实测约 1000 字符）
0.20 < score ≤ 0.34 → 一行提示（id + 标题 + 相关度，实测约 90 字符）—— 明说"未达注入闸门、仅供参考"
score ≤ 0.20        → 什么都不插（不占位）
```

- `hintScore = 0.20` **是量出来的**：11 条真实提问里正确答案的最低分是 0.275，而唯一一条
  "库里真没有对应条目"的提问只有 0.052 —— 两者之间有 0.22 的空档，0.20 落在空档里。
- 提示**看起来就不像已确认的知识**（不给摘要、不给分类、自报"未达闸门"），
  这样模型会把它当线索、而不是当事实。
- 提示也守**会话去重**（`hintedIds`，与 `seenIds` **分开**：提示过的条目将来真命中了
  仍然要能被完整注入，不能被永久压制）和**单回合上限**（`maxHints = 2`）。
- `willInject()` 把"有提示"也算进"会在会话里留下东西"，否则日志会写"没注入"而会话里明明有一行。

### 实测（同一批 11 条真实提问）

| 指标 | 改前 | 改后 |
|---|---|---|
| 完整注入 | 1/11 | 1/11（**闸门没动，噪声不进**） |
| 有可见内容（完整 + 提示） | 1/11 | **10/11** |
| 关键词式对照 | 4/4 | 4/4（未退化） |
| 单次成本 | 完整块 ≈ 1000 字符 | 提示行 ≈ 90 字符 |

提示指向的条目**逐条核对过**：genui 那条 → 提示就是【修正】dsh-ui 围栏降级；
紧缩场那条 → 提示是 时序控制器操作 SOP + 时序控制器调试页 30s 超时兜底；
计划任务那条 → 提示是 计划任务电池静默失败。唯一保持静默的是问 GitHub issues 那条（0.052）——
**库里确实没有对应知识，静默是对的**。

### 已知代价（如实记）

- **闲聊也可能拿到一行提示**（那条 0.338 的 meta 提问）。这是"闸门不降 + 差一点点给提示"
  的必然结果，代价是一行 90 字符、且同一会话不重复。要更保守就把 `hintScore` 调到 0.25 以上
  （会同时丢掉「还是不行，genui还是没有渲染」那条 0.275 —— 实测这个取舍点就在 0.20~0.27 之间）。
- **提示不看内容对不对，只看分**：它解决的是"自动层什么都不给"，不解决"召回的语义准确性"。
  后者要靠上面的 IDF 重构。
