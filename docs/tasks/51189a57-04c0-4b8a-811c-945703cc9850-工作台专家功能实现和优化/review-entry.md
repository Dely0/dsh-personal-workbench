本目录的当前实施版本是 [方案 v0.3](方案-v0.3.md)。v0.2 是历史澄清稿，不作为施工依据。

1. 本文件：理解任务边界和执行方法。
2. [方案 v0.3](方案-v0.3.md) §0–§3：固定范围、架构和契约。

4. 该批指定的规格章节与现有文件；不要把未创建的新路径当当前事实。
5. [验收清单](acceptance.md)：执行对应 AX-E 断言。
6. [证据与状态](verification.md)：区分已核对源码、未实现产品和实际验收结果。
7. [ADR 0009](../../adr/0009-expert-generation-and-invocation.md)：理解决定及对旧 ADR 的影响；当前 proposed。

## 2. 执行模型不可自行改变的决定

- 生成式新建专家；不做市场同步、镜像、更新检测。
- 独立生成会话直接 sessions.create，不能用 connectWorkspace 复用 blank。
- 新角色固定 generated/<服务端 UUID>；来源不参与持久 ID。
- 普通 persona 的固定会话绑定不变；中途使用专家为 spawn 子代理。
- 子代理先加载人格工具，再处理任务；不能直接把正文塞 persona 参数。
- 下载 skill 用 rank 600 provider；不用 runtime register。
- pending 草稿先暂存，用户确认后发布；journal 与 publication 门必须实现。
- 默认关闭自主召唤；关闭时手动 @ /expert 仍能运行。
- 许可原文与版权声明完整保存；追溯信息不能代替它们。
- root 路径由宿主现有目录约定解析；无任意绝对路径工具参数。
- 不改 SCHEMA_VERSION；只补 seed/meta/payload。
- 顶层 inject 不新增可选服务；普通工作台不能因专家增量能力缺失而 pending。

## 3. 批次交接与停止点

按 P0→P1→…→P9 顺序。一个批次结束后写实际交接，等待下一项执行指令。用户要求多个批次时可顺序推进，但不得省略中间检查。

遇到以下情况应明确报告具体问题，不“自行修复”成另一个产品：

- 真正运行的 SDK 没有规格依赖的公开接口。
- install journal 无法判断文件所有权或有用户手动修改。
- 真实模型未调用子代理人格 loader。
- 检查命令失败、测试缺失、旧 lib 与新 src 不一致。
- 目标重启实例等于当前会话实例，或目标 profile/DB 无法核验。

这些都不授权发布、覆盖用户文件或重启当前实例。

## 4. 评审者核查重点

- 生成、暂存、确认、ready 的状态和可见性是否一致。
- 同一确认是否创建一次；跨目录故障是否按 DB commit 分界恢复。
- 子代理第一轮是否能加载正文；父绑定是否从未改动。
- rank 和 scope 是否按真实 SDK 生效；安装后是否 invalidate。
- 开关关闭是否去掉自主 schema/prompt而保持手动入口。
- 未运行的真实 SDK/LLM 断言是否如实记为未验证。

本轮交付为细化文档，不把“设计完成”写成“专家功能已经完成”。
