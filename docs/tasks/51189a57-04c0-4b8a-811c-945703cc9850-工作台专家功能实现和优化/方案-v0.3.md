## 1. 范围、默认值与已经选定的方案

### 1.1 本期必须完成

- 设置 → 角色库 → 新建专家：输入需求、选择已有工作区，建立独立生成会话。
- 生成会话按随包方法论寻找素材、中文化、裁剪/改写，并用工作台工具提交专家草稿。
- 支持给这份草稿暂存人格资源、来源许可和需要的文本型 skill 包。
- 用户可以预览、继续让 AI 修改、重新校验、拒绝、暂存、确认安装。
- 确认后发布到用户专家库和工作台技能目录，可靠处理重复确认和中断恢复。
- 设置页展示内置、外部、用户专家，包括格式错误、停用、依赖不可用等原因。
- 新会话仍使用现有绑定；会话中途通过 @ 或 /expert 让独立子代理使用专家。
- 模型自主发现/召唤专家是单独开关，默认 false；手动入口始终不受这个开关影响。

### 1.2 后续增量，本期不得偷偷实现

- 冻结推荐清单：保留扩展位置，但本期不把 503 条 catalog 打包成市场。
- 第三方专家插件共存验证、镜像管理、上游更新检测、批量导入。
- 修改/覆盖已安装专家、安装时覆盖已有工作台技能、专家删除及技能引用计数。
- 二进制资源、压缩包解压、执行下载脚本、任意 URL 的服务端下载器。
- 持久的专家子会话续聊、后台子代理任务面板、自动重试子代理。
- 为未知的官方未来接口承诺“零数据迁移”。

### 1.3 固定选择与理由

| 决策 | 本版固定值 | 原因 |
|---|---|---|
| 生成入口 | 专用新会话，直接 sessions.create({ workspaceId }) | uiWorkspace.connectWorkspace 会复用空白会话 |
| 方法论投递 | assets/expert-generation/methodology.md，服务端读后投递到这次用户 prompt | 不依赖 skills 服务，不注入所有会话 |
| 人格格式 | 复用 parsePersonaDocument + 现有 Markdown 形态 | 不扩大 frontmatter 白名单 |
| 新专家 ID | generated/<服务端生成的 UUID> | 来源、名称改变不改变身份；不让模型决定写盘路径 |
| 安装模式 | 仅新建，不覆盖已安装角色或技能 | 缩小恢复复杂度；冲突时修改草稿或复用已有 skill |
| 技能挂载 | 工作台自己的 provider，rank = 600 | runtime register 的 rank 250 会盖过用户技能 |
| 中途召唤 | 官方本地 spawn provider + 按需人格加载工具 | 保留现有会话绑定；不注入完整正文或使用 fork 历史 |
| 手动/自主执行 | 手动 request 工具一直在；summon_expert 仅开关开启时注册 | 默认关闭自主功能仍能手动调用 |
| 数据库 | 复用 task_drafts、meta、ai_session_registry；不新增表/迁移 | 本期所需持久数据能装进已有结构 |
| 来源许可 | 机读 provenance + 原版权/许可文件 | 追溯字段不能替代许可材料 |

比较过的两条备选：把全文放进子代理 persona 参数，会绕开正文按需加载，还会遇到模板插值；为子代理预建普通 persona 绑定，官方 subagents.start 请求没有公开的 setup 回调，需要另一套启动实现。本版采用“短 persona 指令 + 子代理专用按需加载”，不改普通绑定 API。

### 1.4 新默认值

| 项 | 默认/限值 | 说明 |
|---|---|---|
| autoSummonExperts | false | meta 键 expert_auto_summon |
| 子代理 provider | spawn | 只接受本地、无父历史继承且满足能力契约的官方 provider |
| 专家正文 | 20000 UTF-16 单元 | 归一化并去除标题/元信息后用现有解析器计算 |
| 人格整文件 | 256 KiB | 与 PERSONA_FILE_MAX_BYTES 一致 |
| 每份暂存文件 | 128 KiB UTF-8 字节 | 仅文本；正文外的归档原件仍按文件大小限制 |
| 每份草稿暂存文件数 | 64 | 不含服务端产生的管理文件 |
| 每份草稿暂存内容总量 | 1 MiB | 人格 + 文件；不把原始内容重复塞进 DB |
| 新安装 skill 数 | 8 | requirements 中 reuse 项最多 16，总项最多 24 |
| 单个 SKILL.md 正文 | 20000 UTF-16 单元 | 本期下载包的提示材料上限，不改变宿主其他 provider |
| 人格资源相对路径深度 | 4 | 与现有附件遍历契约对齐 |
| 方法论修复尝试 | 最多 3 次 | 超过后留草稿和原因，交用户继续描述 |
| 手动 request 有效期 | 创建后 30 分钟 | 执行开始后不按 TTL 中断；同 request 不重复启动 |
| 子代理最长运行 | 10 分钟 | 超时取消并等待 dispose，不后台遗留 |
| 并发专家调用 | 每父会话 1 个，插件实例总计 2 个 | 超出返回 expert-busy；不排隐式长队 |
| 子代理递归 | maxDepth = 父深度 + 1 | 并限制工作台召唤工具在专家子代理里执行 |
| 父会话回传文本 | 最多 12000 UTF-16 单元 | 截断必须标记，附真实 childSessionId |
| 公共 HTTP JSON body | 256 KiB | 复用 readJsonBody；分文件暂存，不扩全局上限 |

这些是本期产品约束，修改它们需同步测试和本规格，不得在实现中随手放宽。

## 3. 数据契约与落盘目录

### 3.1 目录（生产由 homedir 和现有根约定解析）

~~~
~/.dsh/workbench/
  personas/
    .pending/<draftId>/
      files/<personaResourcePath>       # 模型暂存的附件、许可、归档原件
      install-journal.json             # 仅安装器写
      journal.previous.json            # 原子更新的恢复备份
    .install.lock                      # 跨进程安装/恢复锁
    generated/<expertUuid>.md           # 解析器看到的唯一人格文档
    generated/<expertUuid>/
      provenance.json
      publication.json                 # 仅安装器写；ready 后才可发现
      sources/<sourceId>/LICENSE.txt
      sources/<sourceId>/original.md    # 可选，放同名附件内
      resources/...
  skills/
    .pending/<draftId>/<skillName>/...
    <skillName>/
      SKILL.md
      workbench-install.json           # 仅安装器写；关联受管人格
      sources/<sourceId>/LICENSE.txt
      references/... scripts/...
~~~

- 只写工作台两个根；不写 assets/personas、外部角色目录、~/.dsh/skills。
- draftId、expertUuid、sourceId、skillName 都先校验，不能作为任意路径使用。
- UUID 接受标准小写 UUID 字符串；sourceId = [a-z0-9][a-z0-9-]{0,47}；skillName 为小写 kebab-case，1–64 字符。
- generated ID 只由服务端产生，不使用显示名称或上游 repo 作为持久键。
- 人格目录名或显示名改变不在本期管理 UI 支持范围内。
- publication.json、provenance.json、workbench-install.json、install-journal.json 是保留名，模型不能通过暂存工具写这些文件。
- 归档原件可能超过“资源工具 20000 字符”上限；这是归档材料，UI 标“仅归档”。仍保留完整文件，模型试读时由既有工具明确拒绝超限，不截断原件。
- 不将大文本文件内容重复存入 task_drafts；DB 只存 personaMd、结构化元数据、文件索引和哈希。

### 3.2 类型（施工时放 src/shared/expert.ts）

~~~ts
type ExpertCreationKind = 'translated' | 'adapted' | 'merged' | 'original';
type ExpertDraftPhase = 'editing' | 'validated' | 'installing' | 'install-failed';
type ExpertFileArea = 'persona-resource' | 'skill';

interface ExpertSource {
  id: string;
  repository: string;       // HTTPS 仓库首页；不带 token、userinfo、query/hash
  upstreamPath: string;     // 上游相对文件/目录；不得绝对路径或 ..
  commit: string | null;    // 确实取得的 40 位 git SHA；取不到写 null
  fetchedAt: string;        // 可解析的 ISO 时间
  authors: string[];        // 1–16 条，每条 1–200 字符
  license: 'MIT';           // 本期复制/改写素材仅支持已明确 MIT 的来源
  copyrightNotice: string; // 上游原版权声明
  licenseFile: string;      // 本人格附件内 sources/<id>/LICENSE.txt
  usedFor: ('persona' | 'skill')[];
  modifications: string;   // 翻译/裁剪/合并具体说明，不能只写“有修改”
}

interface ExpertProvenance {
  version: 1;
  creationKind: ExpertCreationKind;
  sources: ExpertSource[];  // 0–8；original 可为 0，其他分支至少 1
  references: { title: string; url: string; use: 'background-only' }[];
  generationNote: string;   // 搜索失败、自建、缺 commit 等事实
}

interface ExpertSkillRequirement {
  name: string;
  required: boolean;
  action: 'install' | 'reuse';
  sourceId: string | null;  // install 必须关联 usedFor 含 skill 的 source
  packageFiles: string[];  // install 的完整声明相对文件清单；reuse 固定 []
  reason: string;
}

interface ExpertStagedFile {
  area: ExpertFileArea;
  path: string;            // persona-resource 相对附件根；skill = <name>/<相对路径>
  bytes: number;
  sha256: string;          // 服务端按实际 UTF-8 文件字节计算
}

interface ExpertValidation {
  version: number;         // 哪一版草稿被校验
  manifestHash: string;    // 完整候选安装包的确定性哈希
  checkedAt: string;
  errors: ExpertIssue[];
  warnings: ExpertIssue[];
}

interface ExpertDraftPayload {
  version: 1;             // payload schema version，不是内容 CAS 版本
  contentVersion: number; // 初始 0，每次成功变更 +1
  expertId: string;       // generated/<UUID>
  request: string;        // 用户需求，1–2000 字符
  phase: ExpertDraftPhase;
  personaMd: string;      // 初始为空；提交成功才填
  provenance: ExpertProvenance | null;
  skills: ExpertSkillRequirement[];
  files: ExpertStagedFile[];
  validation: ExpertValidation | null;
  lastInstallError: ExpertIssue | null;
  confirmResult?: ExpertInstallResult;
}

interface ExpertInstallResult {
  kind: 'expert';
  draftId: string;
  expertId: string;
  manifestHash: string;
  installedAt: string;
  installedSkills: string[];
  reusedSkills: string[];
  warnings: ExpertIssue[];
}

interface ExpertIssue {
  code: string; field: string; message: string;
}
~~~

外层 task_drafts.kind_code 固定 expert；外层状态只使用 pending / confirmed / abandoned。phase 是 pending 内部施工阶段，不能新造外层状态。暂存沿用 deferred_at。

workbench-install.json 的固定形状如下；packageHash 按 files（排除管理文件自身）和 SKILL.md 解析元数据计算，文件路径相对 skill 根：

~~~ts
interface WorkbenchSkillInstall {
  version: 1;
  name: string;
  expertId: string;
  installationId: string; // draftId
  packageHash: string;
  files: {path:string;bytes:number;sha256:string}[];
}

interface ExpertInstallJournal {
  version: 1;
  ownerDbKey: string;
  draftId: string;
  expertId: string;
  manifestHash: string;
  phase: 'prepared'|'files-published'|'db-committed'|'ready'|
    'rolling-back'|'rolled-back'|'repair-required';
  createdPaths: ExpertPublishedPath[];
  reusedPaths: ExpertPublishedPath[];
  result: ExpertInstallResult | null;
}

interface ExpertPublishedPath {
  area: 'persona-document'|'persona-directory'|'skill-directory';
  path: string; // 相对对应 personas/skills 根；目录不带尾部 /
  files: {path:string;bytes:number;sha256:string}[]; // 目录内相对路径
}
~~~

日志 paths 也必须重新过路径边界检查，不因“服务端以前写过”而直接信任。persona-document 的 files 固定为当前文档 hash，目录 entries 不含 publication.ready 的可变时间戳。清理 directory 前要验证其中没有未登记的新增文件；发现额外文件就 repair-required，不能递归删除第三方新增内容。

seed 增加 draft_kind/expert（专家安装草稿）和 ai_session_scope/expert_generation；seedDictionaries 的 INSERT OR IGNORE 会补入旧数据库。本期 SCHEMA_VERSION 保持当前值，执行模型不能自行新开迁移。

### 3.3 来源与许可校验

1. 解析 provenance_json 后按版本/字段类型/数组上限验证；非法 JSON 或未知 schema 版本拒绝整份提交。
2. translated/adapted：至少一个 persona 来源；merged：至少两个 persona 来源；original：不允许把已复制材料仅记成 background-only。
3. commit 缺失允许，但给 source-commit-unknown 警告；不允许把 main、HEAD、日期写成 commit。
4. 非 MIT、无许可或只有“开源”口头描述的复制素材不能通过本期校验。可以让生成会话换源或独立创作。
5. 每个 copied source 必须有非空版权声明、原许可文本，以及正确 licenseFile 引用。
6. 对 license 文本只做结构校验：包含原版权声明和 MIT 的 permission 条款，不把该检查称为法律真实性认证。
7. 软件不联网核验模型登记的仓库/commit；预览必须如实显示“来源由生成会话登记”，并允许打开仓库页审阅。
8. persona 与 skill 的版权链各自登记。skill 包须带相应许可副本；不能借人格的一份 license 名字替代 skill 的实际材料。
9. references 仅表示背景阅读；如果原文被复制/实质改写，必须移入 sources 并带许可。
10. 许可要求依据 MIT 原文 https://opensource.org/license/mit；repo/commit/抓取时间是追溯字段，不能替代版权/许可声明。

install 的 packageFiles 必须包含 SKILL.md 和对应 sources/<sourceId>/LICENSE.txt，条目相对该 skill 根，不重复 name 前缀；与暂存索引中该 skill 的路径集合完全一致。缺声明文件或多出未声明文件均报 skill-package-invalid。复制源包是否存在未声明的其他依赖仍由生成会话和用户审阅判断；插件不宣传静态校验能证明所有脚本可执行。

### 3.4 哈希、版本与路径统一规则

- 人格提交先 normalizePersonaText；正文合格后保存规范化人格文本。许可和原件按提交的 UTF-8 全文保存，不做翻译、裁剪或重新排版。
- stage 文件 sha256 对实际写入字节计算；不使用 mtime 作为内容身份。
- manifestHash 输入为稳定 JSON：expertId、persona 文本 SHA-256、provenance、skills、按 area/path 排序的文件 sha256/bytes。递归按对象键代码点排序；数组顺序保留；不包含 checkedAt、phase、lastInstallError、contentVersion。
- 同内容重提交可以保持版本不变并返回 changed:false；内容不同必须清 validation 并令 phase=editing。
- 不允许阶段 installing 的草稿被提交、增删文件、拒绝或暂存。返回 install-in-progress。
- 所有写入先检查根及已有父目录不是 symlink/junction、路径经 resolve 后在根内、realpath 最近存在祖先在根内。最终文件也不能是链接。
- 拒绝盘符、UNC、绝对路径、反斜杠、空段、.、..、NUL、百分号编码、Windows 保留名、尾部点/空格、大小写/NFC 同路径碰撞。
- 复用现有路径形态校验，不自行 decodeURIComponent 后再拼路径。路径错误须带稳定 code。
- 临时文件也放同一目标目录，使用随机名字 + wx 创建，写完 fsync 后 rename；失败只清理本操作拥有的临时文件。

## 4. HTTP 接口（新增前缀 /api/workbench/experts）

所有接口使用 src/api/http.ts 的 isLoopbackRequest/readJsonBody/writeJson。响应不暴露服务端绝对路径、执行 ticket 或真实原始日志。HTTP 只能查看/编辑/确认，不直接启动专家子代理。

复用 PersonaDiagnostic 时只投影 id/sourceKey/code/相对 field；丢弃 path，将 message 中已知根替换为“用户库/外部库/内置库”。FS 异常不把 error.stack 或含绝对路径的原 message 原样外发；服务端日志可保留诊断。该投影只作用于新增专家接口，不借本任务改写其他域的所有错误处理。

### 4.1 接口表

| 方法、路径 | 输入 | 成功响应要点 |
|---|---|---|
| GET /experts/capabilities | 无 | generation、skills、manualSummon、autoSummon 各自 available/reason；providerName |
| GET /experts/catalog | 可选 query；不接根覆盖 | experts 全部管理行；personas 仅可选择的 PersonaSummary；diagnostics |
| GET /experts/methodology | 无 | version:1、text；缺资产返回 methodology-unavailable |
| POST /experts/generation-start | { sessionId, request, workspaceId } | { draft:DraftView }；该 session 一个 pending expert，重复请求回既有草稿 |
| GET /experts/drafts/:id | 无 | draft + 实际暂存清单 + validation；文件漂移明确诊断 |

| POST /settings（既有路径） | { autoSummonExperts:boolean } | 共用 readWorkbenchSettings 重新读取的 settings |

目录已含 /api/workbench；表中 /experts 为简写。没有 PUT/DELETE 已安装专家，也没有任意文件路径读取接口。

### 4.2 关键请求规则

- generation-start：sessionId 1–512、request.trim() 1–2000；workspaceId 必须非空。新建草稿内容版本 0。并发同 session 创建须在 SQLite 短事务内“查已有 → 创建”，不能只在 UI 防连点。
- generation-start 重复同 session 且 request 不同：409 generation-conflict，不覆盖用户之前的需求。
- preflight 的 sessionId 仅作为 HTTP UI 上下文查询；启动子代理仍只能用工具执行上下文 live Agent。无 live Agent 时技能按 global catalog 预检，启动时再按真实 scope/cwd 复核。
- validate 在占用该 draft 的互斥锁后检查 expectedVersion；验证前重读真实文件，禁止只信 DB 文件索引。
- confirm 未通过 validation、版本不同或 hash 不同：409 draft-not-validated / draft-version-conflict / package-changed。
- confirmed 重复 confirm：先恢复 publication，再回放原 confirmResult，不要求客户端仍持有最新版本、不重复创建。
- confirmed 文件被用户改动且无法恢复：503 install-repair-required，不覆盖用户修改、不伪造重放成功。
- 请求体非法 JSON：400 invalid-json；资源超限：413；未知 id：404；能力缺失：503；版本/冲突/正在安装：409。

## 5. 生成工具、方法论与生成会话

### 5.1 工具表

工具命名固定如下。工具 execute 返回可序列化 JSON；output schema 必须真实对应返回值，使用现有 defineTool 的 output 声明。参数里不接 session_id、root、absolute_path。

| 工具 | 参数 | 行为 |
|---|---|---|
| workbench_get_expert_draft | 无 | 依据 exec.agent.session.id 取当前 expert 草稿；返回 id/contentVersion/必要 schema 和清单 |
| workbench_submit_expert_draft | draft_id, expected_version, persona_md, provenance_json, skills_json | 解析校验元数据与人格；成功 CAS 更新；暂存文件保留；清 validation |
| workbench_stage_expert_file | draft_id, expected_version, area, path, content_utf8 | 校验所属会话/版本/路径/限量，原子写暂存文件并更新索引与版本 |
| workbench_remove_expert_staged_file | draft_id, expected_version, area, path | 只删该草稿索引中的暂存文件；更新版本并清 validation |
| workbench_validate_expert_draft | draft_id, expected_version | 重读全包、许可、依赖，返回 errors/warnings/version/hash |

provenance_json 和 skills_json 为 JSON 字符串，具体结构见 §3.2。这样不依赖小模型能正确生成深层工具 schema；服务端仍必须严格解析其真实结构。

每个工具都调用同一个 assertExpertDraftOwner：真实 sessionId 非空；草稿 kind=expert；草稿 sessionId 等于执行 session；外层 pending；版本一致；phase 不在 installing；未知 id 或他会话草稿拒绝。不接模型指定的“当前会话”替代真实执行身份。

成功返回形状：

~~~json
{
  "ok": true,
  "draftId": "服务端 UUID",
  "contentVersion": 3,
  "phase": "editing",
  "changed": true,
  "errors": [],
  "warnings": [],
  "message": "专家草稿已更新，尚未安装。下一次操作使用 contentVersion=3。"
}
~~~

失败返回 ok:false、code、field、message、currentVersion（能合法读取时）。不合格 persona 当场拒绝，不把坏文本写进正式库；可以保留之前的有效草稿。validation errors 非空表示草稿仍待修复，不代表安装成功。

### 5.2 随包方法论的确切内容要求

施工时创建 assets/expert-generation/methodology.md，包含以下按顺序执行的指令，不依赖本地 LS-Skills 或团队记忆文件：

1. 重述用户目标，列职责、输入、输出、边界；需求不足时只问影响产出的关键问题。
2. 调 workbench_get_expert_draft，取得服务端身份和版本；所有后续操作使用工具返回的新版本。
3. 先查当前已安装 skill，按需复用；默认不下载“也许会用到”的整个技能集合。
4. 已知 persona 正源只作为搜索起点：K-Dense-AI/scientific-agents、msitarzewski/agency-agents。相关 skill 从其真实原生上游找；不使用 WorkBuddy 私有正文整理仓。
5. 能访问上游时取得真实路径、commit、版权声明和许可全文。访问失败就记失败；不把“访问失败”写成“没有相应专家”。
6. 选择 translated / adapted / merged / original；翻成中文，但保留关键判断标准、失败边界和技能分工；不要复制长简介填充正文。
7. 人格按 §5.3 模板组织，名称 ≤40、简介 ≤160、正文目标 ≤16000、硬上限 20000；frontmatter 用白名单 group 写显示分组（1–40 字符，没有领域分组就“自建专家”）；技能名写清楚。引用块“分类”不会被现有解析器当 group。
8. 从零生成必须有职责、工作流、检查项、失败/停止条件；将未知专业阈值写成“需用户提供/验证”，不能编造权威数值。
9. 对复制/改写的来源逐条登记；许可原文不翻译、不截断。取不到 commit 写 null，不生成看似真实的 SHA。
10. 调 submit 提交人格和元数据；按文件逐个 stage 许可、资源、所需 skill。遇到 binary/超限/不支持包结构则不安装该 skill，解释缺项；required 项不得静默省略。
11. 每次提交/文件改动后读返回版本；完成后调 validate。按 errors 精确修改，最多 3 轮；禁止绕过解析器或放宽上限。
12. 校验成功后告诉用户“草稿待确认”，列改写方式、来源、必需/可选技能、警告。禁止自行调用确认 HTTP 或通过 shell 写正式库。
13. 网络不可用时可以根据用户需求独立创作并清楚标记；不能把已有受限素材换个标题伪装 original。

这些是生成通道的流程约束，不能被宣传成阻止通用 shell 越权写文件的沙箱。插件保证的是本插件工具和确认路径的写入边界。

### 5.3 人格示例（生成方法论必须带完整最小例子）

~~~markdown
---
group: 工程
---

# 需求审查专家

> 分类：工程
> 工作模式：只读审查
> 建议 emoji：🔎
> 建议简介：审查需求的完整性、可验证性及实现风险，输出明确问题和修改建议。

## 身份与职责
你负责审查用户给出的需求和设计，识别缺失条件、互相矛盾的约束和无法验收的表述。

## 工作流程
1. 提取目标、输入、输出和约束。
2. 核对每个主流程及失败分支。
3. 以严重程度排序问题，给出依据和可以执行的修改。

## 判断与检查
没有代码或运行证据时，不把推测写成已确认事实。
对无法验证的专业阈值，明确指出需要什么证据。

## 技能与资源
本专家没有必需技能。用户另选 skill 时按其说明加载。

## 输出与停止条件
输出结论、问题位置、影响、修正建议和验证办法。
关键输入缺失时先说明缺口；不要编造需求或运行结果。
~~~

实际元信息语法以 parsePersonaDocument fixture 为准；实施必须用该模板跑解析器，若标点不被支持则修正文档资产，不能反向放宽解析器。

### 5.4 客户端精确顺序

1. 打开 ExpertCreateModal；默认从已有工作区中匹配当前会话 cwd，匹配失败就要求用户选一个，不自动创建任务资料夹。
2. 文本为空禁用提交；重复点击由本域 busy 拒绝。
3. GET capabilities；没有 sessions.create 或 methodology 资产时显示原因。
4. GET methodology，在创建会话前确认资产可读。
5. 对已选 workspaceId 调 sessions.create({ workspaceId })，不传 sessionId，不调用 connectWorkspace，不读“当前/最后一条”猜 id。
6. await acquireSession(sessions, id)，成功后 POST generation-start，取得草稿。
7. 使用短上下文 + 方法论全文 + 用户 request 构造这次 prompt；不绑定任务 persona、不复用任何旧业务会话。
8. session.rename('新建专家：' + request 的前 30 字符) 失败不掩盖真正流程；记录可读通知。
9. await session.prompt([{ type:'text', text:prompt }], 'queue')；result.ok===false 时保留草稿并显示错误。
10. 成功后 openSessionInMainView、关闭创建弹窗；每个 await 后检查 isAlive。
11. finally release 引用；失败不删除或归档用户会话。提供“打开生成会话/继续修改”。

提示词里的 draftId 是上下文；工具仍按真实执行会话检查，不相信 prompt 中自述的 sessionId。

## 6. 校验、安装与恢复

### 6.1 校验顺序（validate 和 confirm 复用）

1. 检查草稿 kind、状态、schema/version、当前内容版本。
2. 校验人格 UTF-8 字节上限，调用 parsePersonaDocument；失败直接形成对应 issue。新 generated 草稿另要求解析结果 group.trim() 长度 1–40；不改旧手工/内置人格的 parser 规则。
3. 校验 provenance 结构及每份许可真实文件。
4. 重读暂存索引文件，核对 bytes/sha256、链接/路径、文件数量、总量。
5. 校验 resources 的可读性；仅归档原件超字符上限是 warning，不冒充模型可读资源。
6. 每个 install skill 必须有 SKILL.md、完整声明资源、对应许可；校验 skill frontmatter/正文、文件清单和总量。
7. 查 skills 注册表：reuse 必需项必须存在且 modelInvocable=true；服务缺失时 required reuse 是错误，可选 reuse 是警告。
8. required install 的静态包完整即可允许确认；若当前缺 skills 服务，安装后 catalog 显示“必需技能暂不可用”，不把调用预检判通过。
9. 检查正式目标冲突；已有工作台 skill：同完整清单哈希且已 ready 可复用；不同内容或无管理清单拒绝覆盖。允许模型改成 action=reuse，由用户预览实际生效提供者。
10. 算 manifestHash，写 validation；无 errors 才 phase=validated。

validation 不调用 LLM、不联网、不下载；安装也不做这些工作。confirm 重新执行上述检查，不能只看之前的绿勾。

### 6.2 必需的发布门

新增 src/personas/managed.ts。只对用户根下 ID 精确匹配 generated/<UUID> 的受管角色启用门：同名附件 publication.json 必须 version=1、expertId 一致、ready=true。

缺失/损坏/ready=false：discoverPersonas 和 resolvePersona 共同跳过该文档并给 installation-incomplete 诊断；不能从另一条 resolve 路径读到尚未确认的文件。普通手工角色、内置和外部角色不受此门影响。

provider 对带 workbench-install.json 的 skill 也检查关联人格 publication 标记；没 ready 时不 list/get。旧的手工技能目录可读但不能被安装器覆盖。

这解决跨目录安装途中“文件先出现、用户还没确认成功就被发现”的问题。不能只靠 UI 隐藏按钮。

### 6.3 锁和日志

- 每份 draft 有进程内互斥；所有发布/恢复再取得 personas/.install.lock（wx，跨 profile 共享根）。
- 锁文件记录 pid、owner 随机值、draftId、createdAt；只有 owner 可释放。
- 活进程持有锁：409 install-busy，不等待无限长。
- pid 明确不存在时可回收死锁；pid 存在或不能判断时返回 install-lock-owner-unknown，不强删。人工排障先确认 owner，不提供模型自动 force 参数。
- 暂存写入与拒绝也要检查该 draft 是否安装中，不能与安装同时改源文件。
- install-journal.json 只由安装器写；字段包括 version、draftId、expertId、manifestHash、phase、createdPaths、reusedPaths、每个文件 hash、result。
- journal 必须带 ownerDbKey。真实 DB 用 PRAGMA database_list 的 main.file 解析为绝对、NFC、Windows 大小写归一后的路径并 SHA-256；不把绝对路径放进 journal/HTTP。内存 DB 用构造时生成的实例 UUID（测试可注入固定 identity）。
- 不同 profile 可能共享两个用户库根但使用不同 DB。recover 只操作 ownerDbKey 等于自己的 journal；其他 DB 的日志只跳过，不能因为本 DB 没有那份 draft 就当“未提交”补偿删除。owner 缺失/不可信的日志不做文件操作，记录 install-owner-unknown。
- phase 顺序：prepared → files-published → db-committed → ready；补偿分支为 rolling-back → rolled-back / repair-required。
- 安装构建使用 .pending/<draftId>/.build-persona 和技能暂存根内 .build/<skillName>；从原始暂存文件复制并核对 hash，再 rename 构建件。不能消耗唯一暂存原件，否则补偿/恢复后无法重试。
- 日志原子更新保留上一份可解析备份。根目录不跨卷，文件/目录发布用同根内 rename。
- 本期支持进程中断/异常恢复；不承诺断电造成底层介质损坏后的完整自动恢复。

### 6.4 确认算法（必须按顺序）

1. 获取 draft mutex、发布锁；重新读 DB。
2. 已 confirmed 且有 confirmResult：进入 §6.5 恢复检查，再幂等回放。
3. pending：检查 expectedVersion、validated hash，重新校验并比较实际 hash。
4. 写 prepared 日志并将 phase 改为 installing。记住本次新建/复用路径，禁止把既有目录记为本次拥有。
5. 在 staging 制作完整同名附件（provenance/许可/资源），发布到 generated/<uuid>/；publication 仍未 ready。
6. 对每个新 skill，在暂存包内先写 workbench-install.json，再 rename 到正式 skill 目录；已存在的同哈希 ready 包只记 reused，不重写。
7. 最后发布 generated/<uuid>.md。此时 publication 门仍拒绝发现。
8. 写 files-published 日志。检查所有正式文件哈希与计划一致。
9. 短 SQLite BEGIN IMMEDIATE：CAS 确认这份草稿仍是相同 pending/version；回写 confirmResult、status=confirmed，COMMIT。不要把网络/异步 provider 操作放事务里。
10. 写 db-committed 日志。原子发布 publication.json：

~~~json
{
  "version": 1,
  "expertId": "generated/<uuid>",
  "installationId": "<draftId>",
  "manifestHash": "<sha256>",
  "ready": true,
  "committedAt": "<ISO time>"
}
~~~

11. 写 ready 日志，刷新工作台 provider，返回 ExpertInstallResult。
12. finally 释放自己拥有的锁。provider 刷新失败只写 warning，不撤销已持久安装；下次请求重试挂载。

不要直接把 FS 写入塞进 withDraftConfirm 的 build。它的 ROLLBACK 不会撤销文件。

~~~mermaid
flowchart LR
    A["pending / validated"] --> B["prepared 日志与锁"]
    B --> C["文件已发布，ready=false"]
    C --> D["DB confirmed + confirmResult"]
    D --> E["publication ready=true"]
    E --> F["发现专家、invalidate 技能"]
    C -->|"commit 前失败"| G["只补偿本次新建文件"]
    D -->|"commit 后中断"| H["重启补齐发布，不回滚"]
    H --> E
~~~

### 6.5 失败与恢复决策

| 事实 | 必须行为 |
|---|---|
| DB 未 confirmed，发布前失败 | 草稿仍 pending，回 editing/install-failed；无正式入口 |
| DB 未 confirmed，已有新正式文件 | 仅当路径在本次 createdPaths 且内容哈希仍一致时补偿删除；保留原暂存内容供重试 |
| 补偿发现文件被第三方改动 | 不删除；phase=install-failed，journal=repair-required，显示明确冲突 |
| DB 已 confirmed，publication 未 ready | 不回滚；按日志和实际 hash 完成 publication，刷新 provider |
| DB 已 confirmed，正式文件损坏/丢失，原 stage 完整 | 在无第三方同名占用时恢复本次缺失文件，核对 hash 后 ready |
| DB 已 confirmed，正式文件被用户改成另一内容 | 不覆盖；install-repair-required，标不可用并报告具体相对路径 |
| 重复确认 | 同一个 expertId 和 confirmResult，文件数量不增加 |
| 活锁/无法判断锁 owner | install-busy/owner-unknown，不进入安装 |

启动时先恢复归属本 DB 的可解析专家安装日志，再注册工作台技能 provider。一个 repair-required 条目不得阻止整个插件启动；对应专家隔离并显示原因。读取另一个 profile 已 ready 的人格/技能依靠磁盘 publication，无需其 draft 在当前 DB 存在。

确认操作、catalog 读取和 provider 重新挂载也可触发一次需要的恢复检查，保证“确认成功后崩溃再打开”能收尾。

## 7. 工作台 skill provider

### 7.1 注册与依赖

- 新 provider 名称 personal-workbench。
- 使用 ctx.inject(['skills'], ...) 仅启动子 fiber；不改变 host 顶层 inject。
- registerProvider(create) 工厂中保存 control.invalidate 和 signal；按 effect disposer 释放。
- 禁止逐条 ctx.skills.register 注册下载的技能；那条路径的 runtime rank 为 250。
- 不静态 runtime import dsh-skill-filesystem；只用已验证的服务形状。新增 yaml 普通库依赖用于 frontmatter，固定 yaml 2.9.1（本机宿主实际安装版本）；这是解析库，不是第三方 DSH 插件。
- 为真实技能 scope 查询使用官方公共 scopeOf：@deepseek-ai/dsh-scope 开发依赖 0.2.0-rc.2，optional peer 范围 ^0.1.0-rc.1 || ^0.2.0-rc.1；生产只在需要时动态 import。较旧服务/模块没有所需公开函数时给 skill-scope-unavailable，不在顶层 import 导致插件启动失败。peer 范围表示安装候选范围，具体功能仍按形状检查，不宣称版本范围内全部运行验证通过。
- skills 服务缺失时插件和人格生成照常工作；安装文件可以保留，required 依赖不能被 catalog/preflight 判为可用。
- 服务后注册或重载时子 fiber 重新挂载，control.invalidate 生命周期必须跟着注册实例，不保留旧控制器。

### 7.2 list / get

list(options)：

1. 检查 abort；只扫 workbench/skills 的直接可见目录；跳过 .pending 和隐藏项。
2. 拒绝目录/文件链接；受管安装校验 ready 标记。
3. 解析 SKILL.md：要求 name 和非空 description；name 与目录名相同；正文非空。
4. 使用 YAML parseDocument，拒绝解析错误、非顶层 map、重复 key；使用 core schema；禁用 custom tags/对象构造，toJS 的 maxAliasCount=0。
5. 保留 metadata 对象，不把 YAML 嵌套内容塞进字符串或错误丢弃。未知 metadata 可作为数据保留，invocation 控制键必须严格按下述规则解析。
6. 接受宿主规范键 disable-model-invocation、user-invocable；接受宿主对应 true/false/1/0/yes/no/on/off 字符串，不能用 Boolean('false')。
7. 拒绝 legacy keys disableModelInvocation、modelInvocable、userInvocable；给具体错误。
8. 返回 candidate：name、description、whenToUse（可选）、invocation、source='bundled'、provider='personal-workbench'、rank=600、resourceBase={kind:'directory',path:skillDir}、path=SKILL.md 绝对路径、locator={name,packageHash}、metadata。
9. 只返回验证过的候选；坏包记录 catalog diagnostics，不让整目录 500。

get(candidate, options)：

- 不信任 locator 的任意 path，只允许 name 从自己的根重算。
- 复核 ready、真实文件、清单 hash；与 list 的 packageHash 不符返回 undefined 并 invalidate，不返回新版本冒充旧候选。
- 返回正文（去 frontmatter、trim）及与 list 同一份摘要字段。
- provider 的绝对资源路径只供宿主工具在注册表内使用，不透出工作台 catalog 的 HTTP 视图。

### 7.3 生效来源

同一 scope layer 内 100/200 项目技能优先于 400 用户技能，再优先于工作台 600。不同 scope 的最近层先胜出，不能只按 rank 解释全局所有冲突。

catalog/preflight 调 skills.list/get 时显式传 scope=scopeOf(exec.agent.ctx)、cwd=exec.agent.session.header.cwd、signal；root registry 不会从 Agent 自动推导 scope。HTTP 无 live agent 时标 preliminary，不能拿 global 查询代替最终预检。返回所需技能的 actualProvider、actualSource 和 modelInvocable；若当前 winner 不是工作台下载版本，给 skill-shadowed 警告，不能强行改名绕过用户覆盖。

安装后立即 invalidate；再次 list 必须发现新包。用户手动改工作台技能后的刷新按钮也 invalidate，禁止把缓存永久视作磁盘事实。

## 8. 会话中召唤专家

### 8.1 单一服务接口

~~~ts
interface ExpertInvocationService {
  createManualRequest(input: {
    sessionId: string; personaId: string;
    expectedSourceKey: string; expectedRevision: string;
  }): { requestId: string; expiresAt: string };
  runManual(requestId: string, task: string, exec: LiveExpertExec): Promise<ExpertInvocationResult>;
  runAuto(personaId: string, task: string, exec: LiveExpertExec): Promise<ExpertInvocationResult>;
  loadForChild(ticket: string, exec: LiveExpertExec): Promise<ExpertLoadResult>;
  readForChild(ticket: string, path: string, exec: LiveExpertExec): Promise<ExpertResourceResult>;
  dispose(): Promise<void>;
}
~~~

LiveExpertExec.agent 必须是真实 live Agent，包含 session.id、session.header、ctx；signal 来自工具执行。启动请求绝不使用模型传入的父 sessionId。

### 8.2 始终存在与可选的工具

| 工具 | 默认注册 | 参数 | 守卫 |
|---|---|---|---|
| workbench_run_expert_request | 是 | request_id、task | request 所属父 session、TTL、专家身份、并发、能力 |
| workbench_load_invoked_expert | 是 | ticket | 仅匹配父关系的专家子代理，绑定一次 child id |
| workbench_read_invoked_expert_resource | 是 | ticket、path | 同一 child + 同一专家来源/revision + 资源边界 |
| summon_expert | 否 | persona_id、task | autoSummonExperts 仍 true、live Agent、专家可用 |

自动开关开启才注册 summon_expert 和自主专家提示区块；关闭时调用 disposer。执行函数还重新读 meta，防关闭前已接受的延迟调用继续启动。已启动的调用可完成；关闭不杀手动任务。

开关值只存一个 meta 键；readExpertSettings / writeExpertSettings / service.setAutoEnabled 共用，不另写客户端 localStorage 的“实际状态”。

自主提示区块 name='plugin:workbench-experts'、order=320、interpolate=false，text 为同步函数，每次 assemble 重读已发布且未停用的人格摘要。收藏优先、ID 排序，最多 30 条、简介每条最多 80 字符、总文本最多 6000；明确显示所列 N/总 M，更多由用户手动 @ 指定。摘要是候选信息，required 依赖仍在实际调用前异步复核；不得在同步 text 回调里返回 Promise。关掉时整个 section disposer 释放。

### 8.3 @ 候选和引用形态

- 注册 trigger='@'、name='workbench-expert'、order=20 的独立 source；不覆盖内置文件/会话引用。
- candidate.name 用 'expert:' + personaId；label 显示专家名称；description 用简介；value 放严格 JSON 的 personaId/sourceKey/revision。
- 不实现 matchSpace / matchEnter，不抢内置文件路径的快捷仲裁；仅用户菜单选择产生专家引用。
- onPick 是同步函数，不能 await HTTP。把 pick.session.sessionId 与候选身份组成 ref 的版本化 JSON，返回 {insert:{source:'workbench-expert',ref,label,appearance:'session',clipboardText:...}}。
- ref 形状：{version:1,sessionId,personaId,sourceKey,revision}。不得缓存 ClientSessionContext 当作当前会话对象。
- codec.clipboardText 输出可读文本 '@expert:<personaId>'；纯文本粘贴不自动授予手动 request，用户重新选菜单或使用 /expert。
- codec.serialize(ref, signal) 严格解析 ref，再 POST manual-requests，收到 requestId 后输出下面的短指令；失败抛可读错误以阻止本次发送，不能回落到普通 @ 字符串。

~~~text
【用户指定的工作台专家调用】
用户已在这个会话选择了一位专家。请调用：
workbench_run_expert_request(request_id="<requestId>", task="<按本轮用户消息明确整理的任务>")
这次专家工作由独立子代理完成。不要修改当前会话的专家绑定。
仅处理本轮给定任务；不能把这个 request_id 用于其他任务或其他会话。
~~~

codec 中不注入人格正文。模型仍需把本轮自然语言整理成 task；整理错是模型行为，不算插件已正确完成业务。验收必须观察实际工具参数。

reference 复制到另一会话时，旧 sessionId 的 request 不能在那里执行；返回 manual-request-session-mismatch。不在 serialize 里读取全局“当前会话”替换 ref 身份。

inputTriggers 用子 fiber 软注入；清理时注销 source，不能留下一份重载后重复的注册。

### 8.4 /expert 精确语法

~~~text
/expert <persona-id> -- <任务>
例：/expert generated/aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa -- 审查这份需求的遗漏
~~~

- 以第一个“空格 -- 空格”分隔；左边 trim 是完整逻辑 ID，右边 trim 是任务。
- 不按显示名模糊匹配，不为每个专家注册命令。
- 无参数返回帮助及最多 20 条可用 ID；缺任务返回错误，不启动。
- 从 invocation.agent.session.id 创建同一手动 request。
- agent.steer(createUserMessage(...)) 把含 requestId + 已知 task 的指令送给父会话；工具执行仍走 runManual。
- handler 可 async，但不另写一条直接 start 子代理的路径；/workbench 原语义不改。

### 8.5 子代理按需加载（解决首次 prompt 的时序）

1. runManual/runAuto 校验真实父 Agent、task 1–12000、身份和 required skills。
2. 每父会话最多一个；登记共享 Promise，重复 request 执行等待同一结果。
3. host-adapter 软探测 subagents；只选名字 spawn 且 inheritsParentContext=false，persona/toolFilter/depthLimit 均 true 的本地 provider。不把其他支持 persona 的远程 provider 当作等价实现。
4. 生成随机 32 字节十六进制 ticket（不是 personaId）；内存上下文记录父 sessionId、personaId、sourceKey、revision、resourceDir、允许子 id 初始 null、expires/active。
5. subagents.start('spawn', { parent:exec.agent, signal, prompt:[{type:'text',text:task和输出要求}], persona:短加载指令, maxDepth:父深度+1, toolFilter:... })。
6. persona 短指令只包含静态句子和十六进制 ticket：

~~~text
你是本次工作台专家子代理。
处理任务前必须先调用 workbench_load_invoked_expert(ticket="<ticket>")。
加载成功后按其正文工作；资源使用 workbench_read_invoked_expert_resource。
未加载成功必须停止并报告原因。不要调用 workbench_load_persona。
不能再次召唤工作台专家。按用户任务完成后输出结论、依据、限制和下一步。
~~~

7. 不把专家 name、body、用户输入直接拼入 persona 参数，避免其严格 {{...}} 模板插值。人格原文由工具返回。
8. start 可能在返回 run 之前就触发子代理第一轮。loadForChild 先验证 exec.agent.session.header.origin='subagent'、parentSession=登记父 id，再原子 claim ticket 的 child id。
9. 同一 ticket 已 claim 另一 child 时拒绝。父 Agent、普通会话、其他父会话、失效 ticket 都拒绝。
10. start 返回后要求 run.localAgent 存在且 run.id 与已 claim child（若有）一致；不一致取消并报告 adapter-contract-mismatch。
11. 每次 load/read 重新 resolvePersona(expectedRevision)，并比较 sourceKey，禁止中途换源/读取新 revision。不会调用 writePersonaBinding。
12. load 返回人格正文、revision、资源清单、技能需求、边界提醒。第一次成功加载记 loaded=true。
13. read 直接复用 readPersonaResource；不会执行附件脚本。
14. 专家子代理的工作台调用工具由 toolFilter 拒绝，包括 summon_expert（当前存在时）、workbench_run_expert_request、所有专家草稿生成工具；只把真实存在的名字放 deny，避免 SDK 对 unknown-name 抛错。
15. invocation 服务本身再次检测活跃 ticket 的 child，不允许该 child 通过新 request 绕过限制。

父深度按本机官方 delegationDepthOf 的公开语义计算：max(agent.session.header.delegationDepth ?? 0, agent.options.subagentDepth ?? 0)。两个存在值均须为非负 safe integer 且不能是 -0；缺失才按顶层 0 处理。maxDepth 取结果 +1 并验证仍为 safe integer。不能读取猜测的 header.subagent 字段。

### 8.6 回传、取消和释放

- foreground 调用 await run.result，不重新 steer 一条重复结果到父会话。工具结果本身就是父模型继续处理的上下文。
- completed 且 loaded=true：取 output 中 text blocks；无文本给 expert-empty-output，不能伪造摘要。
- completed 但未加载：expert-persona-not-loaded，子代理文字只能当“未完成指定人格加载的输出”展示，不算成功。
- 非 completed：ok:false，带 stopReason、公开 diagnostic、可标记为 partial 的文本。
- 拼接文本超 12000 时截断并显式 truncated:true，保留 childSessionId；UI 可打开真实子会话读完整内容。
- 10 分钟超时或 exec.signal 取消：abort 子 signal，等待 run.dispose 达到静止状态，返回 canceled/timeout。
- finally await run.dispose，撤销 ticket、释放并发槽；dispose 失败记清理错误，不能遮盖原调用结果。
- 重复 request 在进程内返回同一 Promise/已完成结果；实例重启后 request 失效，请用户重新选专家，绝不猜恢复并重复扣费。
- request 首次执行记录规范化 task 的 SHA-256；同 request 不同 task 拒绝。自主调用用真实 sessionId + exec.callId 去重，不按任务文本合并两个用户有意发起的独立调用。
- request 内存表最多 256 项，过期/完成先淘汰；运行中的记录不得被容量策略丢弃。

### 8.7 返回形态

~~~json
{
  "ok": true,
  "requestId": "<id或auto调用身份>",
  "personaId": "<id>",
  "sourceKey": "<已校验来源>",
  "revision": "<完整sha256>",
  "childSessionId": "<真实run.id>",
  "stopReason": "completed",
  "personaLoaded": true,
  "text": "<结论正文>",
  "truncated": false,
  "warnings": []
}
~~~

子会话 tool 权限继续由官方父委派策略约束。人格不是提升权限的手段。

## 9. catalog、设置与 UI

### 9.1 管理行与可用性

~~~ts
interface ExpertCatalogRow {
  id: string;
  name: string; description: string; group: string;
  source: 'builtin' | 'external' | 'user';
  sourceKey: string;
  revision: string | null;
  enabled: boolean; favorite: boolean;
  status: 'usable' | 'disabled' | 'invalid' | 'dependency-unavailable' | 'installation-incomplete';
  issues: ExpertIssue[];
  provenance: ExpertProvenance | null;
  provenanceState: 'recorded' | 'unrecorded' | 'invalid';

~~~

- 由 discoverPersonas + 按 id/sourceKey 归并的 diagnostics 构建；格式错误的文件即使无 name，也用相对文件名作为显示名。
- 正常内置/外部/手工用户角色缺 provenance 仍可用，显示“来源未登记”；不补猜上游。

- GET catalog.personas 仅返回 status=usable 的现有 PersonaSummary 形状；不把 diagnostics 当摘要塞进选择器。

- DraftBanner 对 kind=expert 显示专用 ExpertDraftBody，不显示“创建任务”按钮。
- 展示正文、中文名称/简介、创建方式、所有来源与未知 commit 警告、必需/可选 skill、安装/复用决策和校验错误。
- editing：确认按钮禁用，提供“校验”“继续让 AI 修改”；validated：按钮“确认安装专家”；installing：按钮禁用并显示进行中；install-failed：显示原因、可校验重试；abandoned/confirmed 用既有外层状态处理。
- 点击确认传 expectedVersion 和 manifestHash。用户看到的内容版本必须与确认版本一致；版本冲突刷新预览，不能自动确认新内容。
- 继续修改先打开原生成会话；如发送反馈，使用已有 SessionReference 生命周期，不创建新草稿或换 owner。
- 安装成功由 useWorkbenchDrafts 的 onExpertInstalled 回调刷新 useWorkbenchExperts/catalog；回传实际 installedSkills、warnings。
- 不影响任务/日报/知识草稿的旧分派、提醒、暂存与并发确认语义。

## 10. 能力与降级

| 缺失 | 可继续 | 禁止假装完成的行为 |
|---|---|---|
| sessions.create | 浏览专家、已有会话使用 | 新建生成会话；不能复用当前会话冒充独立新会话 |
| 方法论资产 | 浏览/使用已有专家 | 新建入口报 methodology-unavailable |
| inputTriggers | /expert、普通新会话选择 | @ 菜单注册 |
| subagents/spawn/必要能力 | 生成、安装、普通新会话选择 | 手动和自主中途召唤 |
| skills 服务 | 无依赖人格创建/安装 | required 技能可用/召唤通过 |
| 搜索/网络工具 | 独立自建草稿 | 声称已下载正源/核实 commit |
| 某个坏包/repair-required | 其他专家、工作台其他功能 | 把整个插件置 pending 或静默用另一位专家 |

host inject 保持 webServer/systemPrompt/tools/commands；client inject 保持 sessions/workspaces/connection/slots/layout。能力提升通过子 fiber，不提高整个工作台最低版本门。

主路径不依赖第三方插件。SDK 类型缺失可用本项目结构化 Probe 接口；不能为方便 import 一整套宿主 runtime。

### 12.2 服务接线的固定表面

createExpertService({db,ctx,roots?,now?,failpoint?}) 返回一个实例，生产 roots/now/failpoint 不从 HTTP 取值。服务负责下列方法，内部委托对应模块，不能复制逻辑：

~~~ts
interface ExpertService {
  capabilities(): Promise<ExpertCapabilities>;
  methodology(): { version:1; text:string };
  startGeneration(input: {sessionId:string;request:string;workspaceId:string}): DraftView;
  getDraft(id:string): ExpertDraftView;
  submitDraft(input:ExpertSubmitInput, exec:LiveExpertExec): Promise<ExpertOperationResult>;
  stageFile(input:ExpertStageInput, exec:LiveExpertExec): Promise<ExpertOperationResult>;
  removeFile(input:ExpertRemoveInput, exec:LiveExpertExec): Promise<ExpertOperationResult>;
  validateDraft(id:string, expectedVersion:number): Promise<ExpertDraftView>;
  confirmDraft(id:string, expectedVersion:number, manifestHash:string): Promise<ExpertInstallResult>;
  abandonDraft(id:string, expectedVersion:number, reason?:string): Promise<ExpertOperationResult>;
  readStagedFile(id:string, area:ExpertFileArea, path:string): ExpertFileView;
  catalog(query?:string): Promise<ExpertCatalogResponse>;
  preflight(personaId:string, agent?:LiveAgent): Promise<ExpertPreflightResult>;
  createManualRequest(input:ExpertManualInput): ExpertManualRequestView;
  runManual(requestId:string, task:string, exec:LiveExpertExec): Promise<ExpertInvocationResult>;
  runAuto(personaId:string, task:string, exec:LiveExpertExec): Promise<ExpertInvocationResult>;
  loadForChild(ticket:string, exec:LiveExpertExec): Promise<ExpertLoadResult>;
  readForChild(ticket:string, path:string, exec:LiveExpertExec): Promise<ExpertResourceResult>;
  setAutoEnabled(enabled:boolean): void;
  invalidateSkills(): void;
  recover(): Promise<ExpertIssue[]>;
  dispose(): Promise<void>;
}
~~~

所有 Input 类型按对应工具/HTTP 表的字段定义；工具 snake_case 在包装层一次转换成域 camelCase。Result 类型按 §3/§5/§8 的形状定义，不能用 any 掩盖不一致。

capabilities 的 generation.available 只表示服务端方法论/草稿能力；客户端还必须检查 sessions.create。autoSummon 除 available/reason 外带 enabled（唯一设置值）；manualSummon 不读取该开关。

validate/confirm 的 HTTP 用户操作调用 service；工具 validate 在调用前执行同一 owner 守卫。不得为 HTTP 暴露 exec 或 LiveAgent 的任意 JSON 构造入口。

### 12.3 UI 所有权与稳定选择器

useWorkbenchExperts 在 WorkbenchApp 装配层调用，拥有 catalog、loading、error、创建弹窗内容及 busy、auto 开关保存状态。向 SettingsModal/PersonaAdmin 传结果和 actions，禁止 PersonaAdmin 再维护一份相同 catalog。旧 flags 的 personaFlagPatch 流程保留，由本域 action 调用。

useWorkbenchDrafts 继续拥有 pending/deferred/确认后的 dismiss；ExpertDraftBody 不创建第二份草稿生命周期。handleDraftConfirmed 增 expert 分支，调用注入的 onExpertInstalled 重新 fetch catalog。

纯组件 actions：

~~~text
openCreate(), closeCreate(), setCreateRequest(text), setCreateWorkspace(id),
startGeneration(), refreshCatalog(), setAutoEnabled(value),
toggleFavorite(id), toggleDisabled(id),
openGenerationSession(draft), validateDraft(draft), confirmDraft(draft)
~~~

最后三个动作按草稿 owner 所在域组合，不能让组件直接调用宿主的私有 controller。

| 元素 | 属性 |
|---|---|
| 管理区域 | data-wb-experts="admin" |
| 新建按钮 | data-wb-expert-action="create" |
| 创建弹窗 | data-wb-experts="create-modal" |
| 需求输入 | data-wb-expert-field="request" |
