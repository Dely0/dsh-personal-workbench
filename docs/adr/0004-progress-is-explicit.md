# 进度是显式值，不由子任务派生

**Status:** accepted（2026-09-30）

仓库里已有「**所有子任务完成后父任务自动完成**（递归到根）+ 直接完成父任务级联完成后代 +
`pnpm repair` 补齐存量」这套规则。再引入「进度」后，同一条父任务的完成度就有了两个来源：
派生的（子任务比例）与显式的（人或 AI 写的百分比）。两个来源必然给出两个数字。

决定：**进度是显式值** —— 人和 AI 写什么就是什么，界面旁边把「子任务 2/3」作为**旁证**显示，
**不自动改写**显式值。「子任务全部 closed → 父任务自动完成」这条既有**状态**规则保持不动；
不新增正常路径上不可达的「子任务全完成后再询问父任务是否完成」提示。

## Considered Options

- **派生优先**（有子任务就自动算比例）：永远自洽，但那正是本项目最大的 bug 类别
  ——「同一语义两处实现」；且子任务不等权会失真（「写文档」与「发邮件」各算 50%）。
- **全派生**（不许手填、AI 也不许写）：进度条永远不说谎，但用户要的能力没了 ——
  没拆子任务的 bug 修复任务，AI 没法表达「代码改完了，50%」。
- **废掉「父任务自动完成」**：能一并治掉「父任务自己有实质工作量却被自动标完成」这个老毛病，
  但要动 V1.5 核心行为（级联完成 / repair 脚本 / 存量数据），风险最大，另立一轮。

## Consequences

- 会存在「保存的进度 60% 而任务已由既有级联自动完成」；已完成任务隐藏进度条，不把这个保存值自动改成 100。重新打开后仍可读到原显式值。不为该情形增加第二套父任务状态规则。
- 输入的粒度建议用五档（`0 / 25 / 50 / 75 / 100`），存储为 0–99 的整数；
  粒度只是输入便利，**不改变权威源**（仍然是显式值）。
- 「父任务自己有实质工作量」这个老毛病记进 `docs/issues/`，单独一轮再动。
- **「今日投入结束」不自动推进度**：独立状态见 ADR 0007；“完成任务”仍是另一条显式动作。进度只由人或 AI 写。按投入 ÷ 预计耗时自动累加会破坏显式值。
  配套两条：① AI 执行会话提示词要求阶段性推进后主动报进度；② 投入结束且任务进度仍为 0 时，显示“顺便更新任务进度？”与 25/50/75 的显式选择，不默认选中、不猜测 X、不替用户修改。

## 实施契约

字段、校验、草稿投影、子任务旁证与动作分流以 [开发规格](../tasks/36c8e8ef-1104-4e68-b55f-a2a6cc533ab9-工作台插件优化/requirements.md) R-P/R-D 为准。原“输入建议五档”中的 100 是完成动作入口，不是库内数值。
