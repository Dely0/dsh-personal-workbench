# WorkbenchApp 出口判据：结构硬门 + 行数护栏

**Status:** accepted（2026-10-04，用户在工作台拆分的目标讨论中明确选择推荐方案）

## 决定

`WorkbenchApp` 的验收拆成两半：**结构约束是硬门，行数是护栏**。原判据 1 的「本体 ≤600 行，只装配模型、布局、视图和弹窗；不承载业务请求、长 handler、政策判定、轮询或宿主 DOM 操作」拆开表述。

硬门（每条都要能落成会失败的源码扫描断言）：

- `WorkbenchApp` 函数体内直接 `useState(` 计数为 **0**。业务状态一律由域 hook 拥有，主组件只接结果与动作。
- 内 `api(` / `fetch(` 计数为 **0**；若确有例外，必须是一份**显式白名单 + 逐条理由**，不接受"就一处不搬"。
- 内 `setInterval(` / `setTimeout(` 计数为 **0**。
- 单个顶层块（顶层 `const`/`function` 声明体、JSX `return` 块）**≤ 80 行**。

护栏：

- `WorkbenchApp` 行数 **≤ 900**，且**每个迁移批次单调下降**。
- 原值 ≤600 降为**努力目标**，不作为验收门。
- 护栏值在 P6 收尾后按实测校准一次；校准口径是「把已计划的 P6/P7 做完之后的自然结果」，不是重新拍一个整数。

判据 2（`src/client/index.tsx` 最终 <5697 且小于施工起点 5725）与判据 3–6 不变。

## Considered Options

- **结构约束升硬门 + 行数降护栏（选中）**：判据 1 的后半句是实质、前半句是它的代理指标。把代理指标升格为验收门会诱导「按行数拆」而不是「按职责拆」；而彻底删掉它，又会让本任务失去唯一廉价可复现的收尾信号。
- **只留结构约束、彻底不设行数**：口径最干净，但把「收了尾没有」这个信号也删了。本任务最大的风险不是拆过头，而是**永远收不了尾**（P1–P5-2 全部未 commit、未装盘），行数是目前唯一能拦住「P7 可以再等等」的量化信号。
- **维持 ≤600 硬门、只放宽解释口径**：放宽口径只能解释数字，不能消除诱导。实测两个反例：`const dayPanelProps = {` 41 行、`const ideasAll = ideas.allIdeas` 98 行都是 props 拼装，为了减行数把它们提成组件，只会把 41 行变成 60 行 + 6 个新 props，没有一个调用点因此变清楚。

## Consequences

- 五条硬门与护栏要落进 P7 出口自检脚本，成为会失败的断言；未达成前 P7 不算完成。实施明细见 [开发规格与验证](../tasks/8e5ea61d-0021-4317-8398-419b8501e6a9-D17客户端拆分/verification.md)。
- 讨论中顺带确认的真缺陷：`const startAISession = async (mode: 'clarify' | 'consult' | 'breakdown' …)`（P5-2 快照为 `src/client/index.tsx:759–1258`，500 行）直接违反「不承载长 handler」。**无论判据怎么定它都要走**，随 P6 的 AI 会话域搬走；它与行数之争无关，不得被压进讨论结论里含糊过去。
- 判据 1 的原文改写为「结构硬门 + 行数护栏」并指向本 ADR，[拆分设计](../design/2026-09-09-client-split-backlog.md) §2.1 与 §7 的 P7 行同步。
- P5-2 后的实测基线（用于校准护栏）：`WorkbenchApp` 2471 行，其中 JSX 676 行、其余装配 1794 行；内直接 `useState(` 34 项、`api(` 32 处、`setInterval(` 2 处。34 项 state 全部属于 P5-3/P6 的域，P7 清单里没有任何 state —— 即 P7 是纯 JSX 与装配收口。
