## 3. 逐条变更

### 3.1 入口收口：`index.tsx` 5725 → 1972

新增模块（都在 `src/client/` 下，无新依赖、无 Context、无全局 store）：

| 目录 | 内容 |
|---|---|
| `hooks/` | 16 个域 hook：知识、点子、任务列表、任务详情、任务表单、任务数据、今日·日历、反馈、设置、提醒、草稿、轮询、导航、快速录入、AI 会话、目录选择（另含 `useWorkbenchBusy`） |
| `views/` | 9 个视图组件：知识列表/详情、点子列表/详情、任务列表、任务详情、任务表单、今日面板、日历 |
| `app/` | `assembly.ts`（装配束 `WorkbenchAssembly`）、`contracts.ts`、`WorkbenchHeader/Overlays/Body/Dialogs`（四段 JSX **逐字搬出**，class 名与 DOM 顺序不变） |
| 根 | `settingsFallback.ts`、`intakeHelpers.ts` |

行数轨迹（每批单调下降，累计 **-3753**）：

```
5725 → 5451 → 5138 → 4754 → 4571 → 4188 → 3724 → 3513 → 2830 → 2814 → 2750 → 2102 → 1980 → 1972
```

**切分规则**（写进 hook 注释，也是本版的核心约定）：请求形状与它的输入校验归**域**；
把结果接到哪些域的状态归**装配层**。视图只接收 `model` + 少量纯函数 / 注入回调，
`hooks/*` 不 import views、不 import 入口，入口只负责组装。

### 3.2 ADR-0008 的结构硬门（落成会失败的断言）

| 硬门 | 实测 |
|---|---|
| `WorkbenchApp` 体内直接 `useState(` | **0** |
| 体内 `api(` | **0** |
| 体内 `fetch(` | **0** |
| 体内 `setInterval(` / `setTimeout(` | **0** |
| 单个顶层块 ≤ 80 行 | 41 个顶层块，**超限 0 个**（最大 66 行） |
| 行数护栏 | 校准为 **≤650**（ADR 原值 ≤900），实测 **631**；ADR 的「≤600」是**努力目标不是门**，未达成（构成分解见交接文档） |

> 校准依据写在 `scripts/lib/d17-p7b-exit-check.py`：ADR 原文要求「护栏值在 P6 收尾后按实测校准一次」，
> 校准为 650 既锁住本批收益，又不给后续微调留伪空间。

### 3.3 判据与反向变异（本版新增的回归防线）

- **15 个出口自检**（`scripts/lib/d17-p*-exit-check.py`，合计 **275 条断言**，全部 exit 0）：
  结构硬门、状态所有权唯一性、「装配层 vs 域 hook」边界、跨域接线（谁把结果接到谁的状态）。
- **15 个反向变异脚本**（`scripts/lib/d17-mutate-p*.py`，全部 **N/N 捕获**）：
  每改坏一处（JSX 回流入口、四段少一段、接线跑回 hook、出现第二个所有者…）都必须被对应判据抓到；
  跑完还原，逐文件 `sha256` 与基线一致。
- 判据纪律：**判据跟着 owner 走**——owner 搬了，正向断言改指新 owner，并从入口侧补一条**负向**断言。

### 3.4 测试基建（夹带项）

- `scripts/verify/suites/day-panel.mjs`：修掉**套件自身的假红**。`dayTab` 是「今日 / 日历」**共用的一份 state**
  （`src/client/hooks/useDayWorkspace.ts:390`），套件此前点了「未排期」（当天 0 行）后没归位就切到日历，
  于是 `AX-T03 主判据`（今日与日历选中今天必须是同一份面板）拿「今日的计划行(2)」比「日历的未排期行(0)」。
  **修法是只归一前置状态（进日历前补一次 `clickTab('计划')`），断言一字未改** —— 改断言求绿会把「判据失效」永久固化。
- `scripts/release-preflight.mjs`：`KNOWN_PROBE_DEBT` 销账（quick-workspace 的 M6/M14 重锚、
  model-picker 的 B7/B8/B10 重锚到新 owner），**变异探针 10/10**，`--phase pre` 可退出 0。
- 6 个变异探针 **0 存活**。

### 发布插曲：`pnpm publish` 打印了 ✅，但实际只是「stage」（npm 2026 的 staged publishing）

**现象（三条独立证据，都用 `curl` / npm CLI 直连原站取得，不看网页）**：

```text
pnpm publish --no-git-checks --access public
  📦 @dely0/dsh-personal-workbench@1.16.3 → https://registry.npmjs.org/
  ✅ Published package @dely0/dsh-personal-workbench@1.16.3      # 退出码 0
```

而同一时刻：

```text
GET https://registry.npmjs.org/@dely0%2fdsh-personal-workbench/1.16.3   → 404
GET …/-/dsh-personal-workbench-1.16.3.tgz                              → 404
GET …/-/package/@dely0/dsh-personal-workbench/dist-tags                → {"latest":"1.16.2"}
packument 的 versions 末三项仍是 1.15.8 / 1.16.0 / 1.16.1 / 1.16.2（`time` 里没有 1.16.3）
```

同版本**重发**给出的诊断性报错，才是真相：

```text
[E409] 409 Conflict - PUT https://registry.npmjs.org/@dely0%2fdsh-personal-workbench
  Cannot publish over previously staged version "1.16.3".
```

**根因**：`scripts/release-preflight.mjs` 用的凭据（团队凭据目录里的 **bypass-2FA 粒度令牌**）
在 npm 2026 的收口下**已不能直接发布**，只能把版本**暂存（stage）**；
npm CLI 在那种情况下照样打印成功、`pnpm publish` 也返回 0 ——
即 skill §7 说的「**退出码 0 不算、网页显示 Published 也不算**」又中了一次，这次的伪装形态是 `✅ Published package`。

**两个附带的坑**：

1. `npm stage list` 用**同一个 bypass-2FA 令牌**查询会返回**空列表**（`[]`），
   看起来像是"什么都没暂存" —— 容易据此误判"发布根本没发生"，进而重复发布（撞 409）。
   判据要用**重发得到的 409 文案**或 `npm stage view`；拿 stage-id 必须切**会话身份**。
2. 本机 `~/.npmrc` 里另有一个 token，但它**已失效**（`npm whoami` → `E401`），
   所以"换个身份重发一次"这条常规解法在本机不成立 —— 必须由维护者做一次交互式登录。

**解法（需要维护者的交互式 2FA，agent 无法代替）**：

```powershell
npm login                 # 交互式登录（会走浏览器 / 2FA），让本机有可用的会话身份
npm stage list            # 列出暂存项，找到 1.16.3 的 stage-id
npm stage approve <id>    # 需要 2FA —— 批准后 1.16.3 才真正公开
# 若决定不发这一版：npm stage reject <id>（把版本号释放出来）
```

批准之后**再**跑一遍 `node scripts/release-preflight.mjs --phase post --version 1.16.3`
（含 tarball 200 + sha1 对账 + 用户视角安装），**然后**才建 GitHub Release。

**发布后复核**（逐条勾，等 npm 公开后执行）：
