# v1.15.4 Release Notes

> 主题：**文档版** —— 把 v1.15.3 的贡献者补进致谢与第三方声明。
> 与 `v1.15.3` **功能完全相同，无代码改动**。
> 上一个稳定点：`v1.15.3`

## ⚠️ 这个版本是一个判断失误，不要当先例

事后用户明确了规矩：**只改文档/配置/测试等"非编译内容"时，不要单独发版** ——
把改动留在工作区，**跟随下一个有代码改动的版本一起发布**。

本版违反了那条规矩。当时我的推理是"npm 页面渲染包内 README，而 npm 不允许覆盖已发布版本,
所以文档修正只能靠新版本号送达"—— 这个事实成立，但**结论错了**：正确的做法是
在发版前把文档核对干净，而不是事后补一个空版本号占坑。
（该规矩已写进 [`docs/release-checklist.md`](../release-checklist.md) 第 5 节第一条。）

**已发布的 v1.15.4 不撤回**（npm 也不允许），但它只是一个已存在的版本号，
不代表"以后文档改动要单独发版"。另外两个相关失误也一并在清单里补了规矩：
Release Title 只写版本号、合入外部贡献时就写致谢（别留到发版）。

## 本版改了什么（留档）

v1.15.3 合入了社区贡献的三项修复，但 README 的致谢段当时**没有补上贡献者** ——
是发版后才发现的。本版补的就是它，仅此而已。

| 文件 | 改动 |
|---|---|
| `README.md` | **致谢**（中英双段）补上 v1.15.3 的贡献者，逐条写清贡献内容与其价值；**版本历史**新增 1.15.4 一行 |
| `THIRD_PARTY_NOTICES.md` | 新增一节，登记该贡献的**可追溯信息**（报告/PR 链接、许可证、逐项改动说明） |

内容要点（致谢里逐条写明了）：

1. **三条建任务路径不建提醒记录**（草稿拆出的子任务 / `POST` 建任务 / `PATCH` 改截止时间）
   —— 这些任务**永远不会提醒**；
2. **投递目标内存缓存**引发的两个连锁缺陷（重启后设置页误报「未配置」，且整个调度器
   **静默跳过**所有到期提醒，含启动补发）—— 报告者引用了 `draft-notify.ts` 里那段
   "草稿通知侧早就绕开同一个坑"的注释作为旁证，一句话说清了"为什么只有任务提醒坏了"；
3. **复用型会话的陈旧引用**（会话被归档/删除后点了没反应，且陈旧引用永不更新、该链路从此开塞）
   —— 除了纯判据 + 表驱动单测，还自己找出了**报告行 `sessionId` 回退**这条独立的第二复用路径。

## 关于 `THIRD_PARTY_NOTICES.md` 为何也登记"贡献"而不只是"第三方代码"

那份文件的定位是"本仓外部作者代码的**可追溯清单**"。贡献进来的代码同样是外部作者所写，
登记在这里不会造成误解（条目开头明确写了 `(contributor, v1.15.3)` 与
"These are **contributed changes, not adapted third-party material**"），
而好处是：以后要查"这段代码是谁写的、依据是什么、有没有许可问题"，
只需要看这一个文件，不必在两处之间来回找。
