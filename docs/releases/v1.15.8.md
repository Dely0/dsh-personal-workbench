# v1.15.8 Release Notes

> 主题：**适配 DSH `0.2.0-rc.1`（桌面端）—— 只改兼容性声明**
>
> DSH `0.2.0-rc.1` 新增了**插件兼容性预检**：它只读插件的 `peerDependencies`，
> 把 `@deepseek-ai/dsh` / `@deepseek-ai/dsh-*` 的区间与当前运行时做
> `semver.satisfies(..., { includePrerelease: true })` 比对，**判不过就把该插件整行
> `disabled = true`（静默禁用）** —— 不报错、服务照常、页面照常，只是插件整体不见了。
> 本版把 4 个 `dsh-*` peer 区间改成**并列区间**，同时覆盖 `0.1.x` 与 `0.2.x`。
>
> 上一个稳定点：`v1.15.7`

## 0. 来源与致谢

本版没有外部代码贡献。问题由维护者在**本机 DSH `0.2.0-rc.1` 桌面端**实测发现，修复与测试由维护者完成；
**发布前已经过用户在本机桌面端重启实测确认**（`0.2.0-rc.1` 桌面壳，工作台入口与面板均正常）。

## 1. 现象与根因

### 现象

桌面端从 `0.1.7-rc.2` 升到 `0.2.0-rc.1` 后，工作台与另外几个第三方插件"不兼容"：

| 观察 | 事实 |
|---|---|
| 启动报错 | **没有** |
| 服务/端口/页面 | **全部正常** |
| 工作台 | 入口、面板、tool、`/workbench` 命令**整体消失** |

即典型的**静默禁用**，最容易被误判成"新版破坏性更新"或"插件坏了"。

### 根因：`0.2.0` 新增的兼容性预检（`0.1.7` 没有这段）

`@deepseek-ai/dsh-app-boot` 里的两个函数：

```js
// evaluatePluginCompatibility(manifest, exemptions, runtimeVersion)
if (name !== '@deepseek-ai/dsh' && !name.startsWith('@deepseek-ai/dsh-')) continue
const requirement = ['workspace:^', 'workspace:~', 'workspace:*'].includes(range)
  ? runtimeVersion : range
if (!semver.satisfies(runtimeVersion, requirement, { includePrerelease: true })) peers[name] = range

// preflight(...) 里
deny(row, reason) { row.disabled = true; if (row.group) row.group = false; report(row, reason) }
```

**只看声明，不做任何 API 探测**。本版此前的区间是 `^0.1.5-rc.1` / `^0.1.0-rc.6`，
在 `0.2.0-rc.1` 上**全部不满足** ⇒ 4 个 peer 全挂 ⇒ 插件被整行禁用。

## 2. 修法：并列区间，**不抬高下界**

```jsonc
"peerDependencies": {
  "@deepseek-ai/cordis":            "^4.0.1",
  "@deepseek-ai/dsh-commands":      "^0.1.5-rc.1 || ^0.2.0-rc.1",
  "@deepseek-ai/dsh-host-webserver":"^0.1.0-rc.6 || ^0.2.0-rc.1",
  "@deepseek-ai/dsh-system-prompt": "^0.1.0-rc.6 || ^0.2.0-rc.1",
  "@deepseek-ai/dsh-tools":         "^0.1.0-rc.6 || ^0.2.0-rc.1"
}
```

实测区间行为（真 `semver`，`includePrerelease: true`）：

| 区间 | `0.1.5-rc.1` | `0.1.7-rc.2` | `0.2.0-rc.1` |
|---|---|---|---|
| `^0.1.5-rc.1`（改前） | ✅ | ✅ | ❌ |
| `^0.2.0-rc.1`（**错误改法**） | ❌ | ❌ | ✅ |
| `^0.1.5-rc.1 \|\| ^0.2.0-rc.1`（本版） | ✅ | ✅ | ✅ |

> ⚠️ **为什么不直接把区间换成 `^0.2.0-rc.1`**：那会把**所有还在 `0.1.x` 上的用户**
> 用同一套新门禁全部挡掉 —— 只是把受害者从我们换成别人。所以下界不动。
>
> `^0.2.0-rc.1` 本身已覆盖 `0.2.x` 后续版本（`0.2.0-rc.2` / `0.2.1` 均满足），无需另开上界。
> 但**核心升到 `0.3` 时会再被挡一次**，这是刻意的：那时需要重新评估。

## 3. 测试：从"等号"改成"区间形状"，并把耦合拆开

原断言是**等号**：

```js
assert.equal(peers['@deepseek-ai/dsh-commands'], `^${MIN_HOST_VERSION}`)   // 已删除
```

它把两件**不同**的事压成了一个常量：

| 概念 | 含义 | 本版结论 |
|---|---|---|
| `MIN_HOST_VERSION` | **运行时能力门槛**（`layout.selectPanel` 从 `0.1.5-rc.1` 起才有） | **不变** |
| peer 区间 | **声明兼容范围** | 改为并列区间 |

新断言（`test/pluginEntry.test.mjs`）钉住的是**形状**，而不是某个具体版本：

1. 区间**必须含**能力门槛 `0.1.5-rc.1`（抬高下界 = 禁用老用户）；
2. 区间**必须含**当前最新核心 `0.2.0-rc.1`（否则工作台在桌面端被静默禁用）；
3. 区间**不得含** `0.1.5-alpha.1` / `0.1.0-rc.5`（下界没被放宽）；
4. 区间**不得退化成** `*` 或 `>=0`；
5. 4 个 `dsh-*` peer 逐条满足 1+2。

> 本仓 `dependencies` 只有 `react`，**没有为一条单测给公开发布的插件加 `semver` 依赖**。
> 测试里实现了一个只认 `^x.y.z`（多段 ` || ` 并列）的极简判定器，
> 并用真 `semver` 逐例校准 **80/80 完全一致**（含 prerelease 语义）。

## 4. 实测证据：`0.2.0-rc.1` **没有破坏性更新**

本版**没有改任何 `lib/` 运行时逻辑** —— 但为了确认"不是把真问题藏起来"，做了两层实测。
对比对象：本机 `0.1.7-rc.2` profile 树 ↔ 从桌面端 `resources/app.asar` 解出的**完整**
`0.2.0-rc.1` 核心树（289 个包）。

| 检查 | 结果 |
|---|---|
| 被移除的包 | **0**（新增 53 个，纯增量） |
| 被移除的 export | **0** |
| `dsh-tools`（工作台 import `defineTool`） | 12/12 文件**逐字节相同** |
| `dsh-llm`（工作台 import `createUserMessage`） | 18/18 **逐字节相同** |
| `dsh-system-prompt` | 2/2 **逐字节相同** |
| `dsh-host-webserver` | `lib/index.js` **相同** |
| `cordis` | 2/2 **逐字节相同** |
| `dsh-commands` | 仅 `lib/typert.host.js`（类型声明产物）不同 |

**真加载验证**（不只是静态比对）：用自定义 ESM `resolve` hook 把插件的
`@deepseek-ai/*` 说明符重定向到目标核心树，再 `import()` **构建产物**：

| 验证层 | `0.1.7-rc.2` | `0.2.0-rc.1` |
|---|---|---|
| 模块图绑定（缺包/缺 export 会直接抛） | ✅ | ✅ |
| `createUserMessage()` 实跑 | ✅ | ✅ 同形状 |
| **13 个真实 tool 过核心的 `defineTool`** | 13/13 | **13/13** |
| 工具名集合 | — | **逐字一致** |

`defineTool` 是关键判据：它**不是透传** —— 在定义时就
`parameterSchemaSpecToJsonSchema(options.parameters)`，参数形状不认识**立刻抛错**。
工作台 13 个工具（11 个 + 知识库 2 个）在 `0.2.0-rc.1` 核心下**全部构造成功、名字完全一致**。

客户端门禁面同样稳定：`dsh-client-ui-slots`（工作台 client 依赖
`inject`/`register`/`entriesOfSlot`）**逐字节相同**（23433 B）；
`dsh-client-ui-layout`（`selectPanel`/`panelInfo`）为 `+391 B` 纯增量。

## 5. 本机装盘与验收（用户已实测确认）

桌面端 profile（`~/.dsh/profiles/desktop`）被 CLI **硬禁**：

```
error: profile "desktop" is managed exclusively by the Electron application
```

（`@deepseek-ai/dsh/lib/bin.js` 的 `rejectElectronProfile()`），因此 `dsh plugin --profile desktop …`
与 `dsh plugin allow-version` **都不可能执行**。实际落地走的是**桌面自带的工具链**
（`runtime` 内 node `24.21.0` + pnpm `11.7.0`，与 `desktop-runtime.json` 声明一致），
对固定路径本地 tgz 做了一次**精确版本重装**：

| 项 | 值 |
|---|---|
| 装盘版本 | `1.15.7`（带新 peer 区间的开发包） |
| `package.json` diff | **只有工作台那一行**（bundle 列表 0 差异） |
| `pnpm-lock.yaml` diff | **只有工作台那一条**（无静默回退） |
| 兼容性门禁复算 | 工作台 `compatible`；硬挡 **0** 个 |

另外 7 个第三方插件（`dsh-genui` / `dsh-agency-agents` / `dsh-skills-manager` /
`dsh-better-sidebar` / `dsh-cost-meter` / `dsh-find-plugin` / `dshmarket`）的 peer 仍锁在 `0.1.x`，
本机用 **exact-version 豁免**（`profiles/desktop/compatibility.json`）应急放行。
⚠️ 豁免是 **exact-version** 的：插件升级版本号后自动失效。
⚠️ 并且那 7 个只做过**静态**核对（其 import 的核心包与 named export 在 `0.2.0` 里都存在），
**没有**像工作台这样真跑一遍 tool/路由 —— 出问题请单独撤销对应那条豁免。

## 7. 依赖与支持边界

- **DSH 最低支持版本不变**（仍是 `0.1.5-rc.1`）；新增支持到 `0.2.0-rc.1`。
- **没有新增 DSH 服务依赖**：`dsh.client.inject` 仍为空数组（`test/capabilities.test.mjs` 锁定）。
- **数据库 schema 未变**（仍是 18）⇒ 本版对数据库没有前进，回退到 `v1.15.7` 不会让宿主拒绝启动。
- ⚠️ **本版 `lib/` 产物与 `v1.15.7` 内容完全相同**，包内容差异只有 `package.json` 的
  `peerDependencies`。之所以必须发新版本号：**npm 不允许覆盖已发布版本**，
  而 `0.2.0-rc.1` 上的用户只有拿到新版本才能通过预检。
  换言之这是一次**为"兼容性声明"而发的版本**，不是为 `lib/` 变更而发。
- "内容完全相同"是**实测**的，不是推断：拉回 npm 上的 `1.15.7` 真实产物后，
  与开发树 `lib/` 逐文件比对 —— **185 个文件全部一致**。
  其中 `knowledge-recall-log.js` / `reminder/draft-notify.js` 两个文件**哈希不同但内容相同**，
  原因是**行尾差异**（CRLF），归一化后哈希逐一相等。另有 `scripts/check-installed-fingerprint.mjs`
  的结论可佐证：**开发树与装盘产物 185 vs 185 文件全部同内容**（它报 ❌ 只是因为
  profile 当前仍声明 `1.15.7` 而开发树已是 `1.15.8` —— 即**版本号差异，不是代码差异**）。

## 8. 验收方式

1. 在 DSH `0.2.0-rc.1` 上安装 `1.15.8`（或带新 peer 区间的开发包）后重启宿主。
2. 侧栏应出现**工作台**入口；打开面板可正常显示、可关闭。
3. 真发一条消息 / 建一条任务，确认 tool 与 `/workbench` 命令都在。
4. 若工作台**仍然整体消失**：说明宿主版本已超出声明的区间（例如核心升到 `0.3.x`），
   此时需要重新评估并发布新的 peer 区间 —— 这**不是**本版回归。

## 9. 已知问题 / 未覆盖

- 那 7 个第三方插件依赖"用户主动授豁免"才能在本机跑起来，**本版不解决它们的兼容性**。
- `0.2.0-rc.1` 新增的 53 个包（agent-preset / ptc-runtime / plugin-manager / office-to-skill /
  workspace-changes 等）**本版没有做功能适配**，只是确认它们的加入不破坏既有接线。
- 未验证 `0.2.0-rc.1` 上**客户端**的槽位渲染在真实浏览器里的表现（agent 侧无法免登录打开 GUI）——
  本机由用户重启后肉眼确认通过。
