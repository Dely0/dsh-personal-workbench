# v1.15.5 Release Notes

> 主题：**适配 DSH 0.1.7-rc.2（桌面端）** —— 宿主在同一个大版本里改了三处会话契约、两处 DOM 几何，
> 客户端有两处「同一语义在多个入口各写一遍」，于是升级后**五类报错同时出现**。本版全部收敛到唯一实现。
>
> 上一个稳定点：`v1.15.4`

## 0. 来源与致谢

本版没有外部代码贡献。问题由维护者在本机 DSH 0.1.7-rc.2 桌面端实测发现（四项现象）
并在核对宿主 bundle 时又坐实两项（见 §5），修复与测试由维护者完成。

宿主契约的判据全部来自**读宿主自身的客户端 bundle**（`app.asar` 内）与官方类型定义，
不靠猜；同环境里能正常工作的第三方插件（`dsh-better-sidebar`）的实现被用作交叉验证。

## 1. 快速录入 / 澄清会话报「会话绑定未就绪，请稍后重试」

**现象**：点「快速录入」→ 创建澄清会话，直接抛错，整条澄清链路不可用。

**原因**：宿主把 `sessions.binding(id)` 的语义改了。

| 宿主 | `sessions.binding(id)` 的判据 |
|---|---|
| ≤ `0.1.5` | "在会话列表里 **或** 是当前会话" → 刚 `create()` 出来的会话能拿到 |
| `0.1.7-rc.2` | **只查已被 `retain()` 的 scope**：没人 retain 就恒为 `undefined` |

而 `uiWorkspace.connectWorkspace()` 内部只是 `sessions.create()` —— **谁都没 retain**。
官方类型注释写得很清楚：*"Callers **retain** the returned identity before borrowing its binding."*

**修法**：新增 `src/client/sessionRef.ts#acquireSession()` 作为**唯一**取会话引用的入口。

1. 宿主有 `retain`：`retain(id, {source})` → `await ref.ready` → **提前取出** `ref.binding.session`
   （引用被 `release()` 之后再读 `binding` 会抛）→ 调用方在 `finally` 里 `release()`，与引用计数配对；
2. 旧宿主没有 `retain`：回落 `binding(id)`，释放是 no-op。

## 2. 澄清能发出去、界面却报 `?.open is not a function`

**现象**：会话建好了、AI 也回了，但每点一次都报错。因为流程是
「发消息 → 登记 → **切主视图** → 收面板」，报错发生在倒数第二步：
**功能和错误同时存在**，用户看到的是"能用了但又报错"。

**原因**：宿主**整个移除**了 `sessions.open(id)`。

| 宿主 | 切主视图的入口 |
|---|---|
| ≤ `0.1.5` | `sessions.open(id)`（内部 `manager.select`） |
| `0.1.7-rc.2` | **没有 `open`**；官方口径是 `uiWorkspace.openSession(target)`（内部 `retain(id,{source:'mainView'})` + 选中，并释放上一条 mainView 引用） |

**为什么炸得这么广**：这个语义原先在 `index.tsx` 里抄了 **4 遍**、`DraftBanner.tsx` 里还有 1 遍 ——
升级后**5 个入口同时报错**（快速录入 / 复用的计划·日报·点子会话 / 会话页签「打开 ↗」 /
已完成任务的「进入复盘会话」/ 草稿横幅「回到会话」）。

**修法**：新增 `sessionRef.ts#openSessionInMainView()` 作为**唯一**实现 ——
`ctx.get('uiWorkspace')?.openSession(id)` 优先，回落 `sessions.open?.(id)`，两条都没有则抛可读错误。
`uiWorkspace.openSession` **两版宿主都有**（`0.1.5` 里它就是 `sessions.open` 的包装），所以这个顺序两版都安全。

⚠️ **刻意不自己 `retain(id,{source:'mainView'})` 模拟**：宿主布局是按
「谁被 mainView retain 着」找当前会话的，手动 retain 会与宿主自己那条**同时存在**
（两个 `retainedBy.mainView > 0`，宿主 `find()` 取谁就变得不确定）。

## 3. 面板顶部压住桌面端标题栏，窗口按钮点不动

**原因**：`0.1.7-rc.2` 桌面壳在 `<html>` 上加 `data-windows-titlebar`，给内容区加了
`padding-top: var(--dsh-windows-titlebar-height)`，并铺了一条 `-webkit-app-region: drag` 的标题栏
（窗口按钮就在那条带子里）。而工作台面板挂在 `shell.overlay` 下、自己 `position:fixed`，
**不跟着那个 padding 走** → 面板内容正好压在标题栏上。

**修法**：面板上边界改由 `--wb-top-inset` 驱动，取值来自纯函数
`src/client/panelGeometry.ts#decideTopInset()`：没有桌面壳标记 → `0`；
有标记 → 优先取 frame 的计算 `padding-top`，再退宿主的变量值，最后兜底 32px
（与 `dsh-better-sidebar` 对"Electron 无 WCO 窗口"的既有取值一致）。

普通网页版 / macOS / 老宿主没有该属性 → 让位值为 0，**行为与改动前完全一致**。

## 4. 收起侧栏后工作台铺不满（左边界停在 280px）

**原因**：旧口径（v1.14.21）把"量到 0"当成**量取失败**、不更新变量
（`if (width <= 0 || width > 视口40%) return`）。而 rc2 收起侧栏时**栏目宽度就是 0** ——
于是 `--wb-sidebar-w` 永远停在收起前的旧值，面板左边空出一条。

**修法**：判据抽成纯函数 `panelGeometry.ts#decideSidebarWidth()`：

| 情形 | 结果 |
|---|---|
| 找不到侧栏容器 | 不更新（保留上一次的值：兜底 280px 远好过 0px 盖住侧栏） |
| 宿主公布了宽度（rc2 把权威值写在 frame 上） | **采信它**（收起时即 0） |
| 几何量到 ≤ 0 | **采信 0**（这就是收起状态） |
| 宽过视口 40% | 判为量错元素、不更新 |

同时盯两个信号：侧栏列的 `ResizeObserver` + frame 上 `data-sidebar-collapsed` 的**属性观察器**
（属性先变、几何还要走 300ms 过渡）。

## 5. 顺带修掉一处既存静默丢件（两版宿主都存在）

> 这是**核对宿主契约时发现的老 bug**，不是 rc2 引起的；因为它就在本次改动的同一段
> 「选工作区」逻辑里，且属于"静默忽略用户的选择"，故同版修掉。

`workspaces.create()` 返回的是宿主**生成式 Remote 结果**，形状是
`{ ok: true, value: { workspace: { workspaceId, path, … } } }` ——
而工作台从 v1.14 起读的是顶层 `created.workspaceId`，**该字段两版宿主都从没存在过**。

**后果不是崩溃，而是静默忽略用户显式选的 AI 会话工作区**：`create()` 明明成功建/取到了工作区，
我们没读出 id → 落回 `pickIntakeWorkspace()`（按当前会话 cwd / 唯一候选猜）。

**修法**：纯函数 `src/client/intakeWorkspace.ts#readCreatedWorkspaceId()` 负责读取（带单测），
并且**读不出来时显式报错**，不再假装成功。

## 6. 破坏性变更

无。所有改动都在客户端，且都按"新宿主优先、旧宿主回落"的顺序判定：

- 没有 `data-windows-titlebar` 的宿主 → 上边界仍是 `0`；
- 有 `sessions.open` 没有 `uiWorkspace.openSession` 的宿主（理论上不存在） → 回落旧路径；
- 侧栏宽度的取值口径变了，但只在"几何量为 0"这一档与旧行为不同 —— 而那正是要修的情形。

数据库 **schema 不变**（仍为 18），本版可在旧库上直接升级。

## 7. 依赖与支持边界

- DSH：`0.1.5-rc.1` 及以上（Web 版）；**`0.1.7-rc.2` 桌面端已实测**。
- 本版新增一档可选能力：`sessions.retain()`（`0.1.7-rc.2+`）—— 拿不到时自动回落 `sessions.binding()`。
- `uiWorkspace.openSession`：`0.1.5-rc.1+` 都有（`0.1.5` 里是 `sessions.open` 的包装）。

## 8. 验收方式

维护者本机（DSH `0.1.7-rc.2` 桌面端）逐条走过：

1. 「快速录入」→ 创建澄清会话：**不再报「会话绑定未就绪」**，且会话被切到主视图；
2. 面板顶部不再压住标题栏，窗口按钮可点；
3. 收起左侧栏后工作台跟随铺满。

机械验收（发布前跑过，退出码全 0）：

| 项 | 结果 |
|---|---|
| `pnpm typecheck` | 0 |
| `pnpm test` | **568 / 568 通过**（上一版 534） |
| `check-installed-fingerprint.mjs` | 开发树 `lib/` 与装盘产物 **181 个文件逐文件 SHA256 一致** |
| `check-installed-version.mjs` | 装盘 / 声明 / 锁文件 / 数据库 schema 四者一致 |

## 9. 已知问题

1. **健康端点只报版本号**：本地 dev 迭代常常同版本号反复装盘，
   `/api/workbench/health` 无法区分"装的是哪一次构建"。要精确判断请用
   `scripts/check-installed-fingerprint.mjs`（把构建戳写进健康端点是待办）。
2. **两处已失效的宿主面**（本版已核实、未改，均有守卫，不会误用）：
   - `connection.generation.getSnapshot()`：rc2 的 connection 服务只剩
     `start({source, sinks, recovery, config})`，host home 只交给"拥有 generation source"的一方。
     工作台的 WSL 判断有全链 `?.` + try/catch，会**安全退化**为"按工作区路径猜 WSL"；
   - `workspaces.openPath`：`0.1.5` 与 `0.1.7-rc.2` **都不存在**，
     `connectWorkspace()` 的兜底腿是死路（有 `typeof` 守卫）。
3. **桌面端 profile 无法用 CLI 自检**：`dsh --profile desktop --dump-config` 会被拒绝
   （该 profile 由 Electron 应用独占管理）。桌面端的"插件树能组装"只能靠
   「manifest 与 bundles 未变 + 指纹一致 + 应用自己启动」三条间接证明。
