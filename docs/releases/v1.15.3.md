## 1. 提醒：补齐三种建任务路径（#4）

`addReminder` 原先只有两个调用点：草稿确认时的**父任务**、以及手动 `POST /tasks/:id/reminders`。
于是下列三条路径建出来的任务**永远不会提醒**（调度器只从 `task_reminders` 读）：

| 路径 | 现象 |
|---|---|
| 草稿拆出的**子任务**（`walkChildren`） | 父任务有提醒、所有子任务 `reminders: []` |
| `POST /api/workbench/tasks` | 建出来的任务没有提醒记录 |
| `PATCH /api/workbench/tasks/:id` 改/设截止时间 | 仍没有提醒记录 |

**修法**：三处统一按与父任务一致的落点补建 —— 显式 offset → `type.defaultReminderMinutes` →
`priority.defaultReminderMinutes`，且只在 `dueAt !== null` 且 offset 是 `>= 0` 的有限数字时才建；
`PATCH` 额外判断"该任务当前没有生效中的提醒"以免重复。

> **一个可放心的细节**：提醒是**按 `offset_minutes` 存、按 `dueAt − offset` 现算**的
> （见 `listReminders` 的 SQL），**不是存绝对时间** —— 所以"已有生效提醒就不再加"不会留下过期时间戳。

## 2. 提醒：投递目标缓存导致"重启后所有提醒静默跳过"（#5）

两个看起来无关的现象同一个根因：

- **设置页把已绑定的目标显示成「未配置」**：`adapter.status()` 的 `configured` 读的是内存缓存
  `cachedTarget`，而它**只在 `resolveTarget()` 里填充** —— `GET /reminders/channel` 只调 `listOptions()`，
  从不填充 → 重启后必然 `false`；随手 POST 一次就"恢复"了（因为 POST 分支会 `resolveTarget()`）。
- **重启后所有到期提醒被静默跳过**：`src/index.ts` 的 `isTargetConfigured` 直接读那个缓存，
  于是 `scheduler.ts` 的 `channelReady` 为假、**包括启动补发在内一条都不发**，也不写 `fired_at`。

**旁证（原作者给的，特别有价值）**：`src/reminder/draft-notify.ts:187` 的注释原文就写着
「**不用** isTargetConfigured()——那个读的是适配层的目标缓存，进程刚起来时缓存为空会让通知永远发不出去」。
**草稿通知侧早就绕开了，任务提醒侧漏修。**

**修法**：`isTargetConfigured` 改成"缓存命中 → 数据库有显式绑定"两级；`GET /reminders/channel` 先
`await resolveTarget()` 再回报状态。

## 3. ⚠️ 维护者改判：`isTargetConfigured` 的末行（PR #6 原稿 vs 本版）

PR #6 原稿是**三级**判定，末行 `return adapter.available()`（"装了 dsh-im 就乐观放行"）。
**本版把末行收紧为 `return false`。**

原因：`adapter.available()` 只回答"dsh-im 装没装"，不回答"目标配没配"。于是
**从未绑定过投递目标**的用户会从"什么都不做"变成：

```
每条到期提醒都尝试投递 → 失败(not-configured) → 入队退避 → 反复写 reminder_channel_unavailable
```

**不是丢提醒，是把"安静地不做事"变成"安静地反复失败"。**

而真正要修的那批人（重启后缓存为空但**确实绑过**目标）在收紧后照样修掉 —— 第二级就命中了。

保留的保守取舍：`resolveTarget()` 是**异步**的，所以"没显式绑、但恰好只有一个 bot + 一个 user target"
这种自动发现场景第一次仍返回 `false`（下一轮 tick 缓存命中后恢复）。宁可晚一轮，也不给没绑目标的用户制造噪声。

**反向验证**：新增 `test/reminderWiring.test.mjs`（3 条源码级不变量），其中第一条就是"闭包体内不得出现
`available()`"。实测把 `return adapter.available()` 装回去 → 该断言**变红**；还原后 3/3 绿。

## 4. 复用型会话的陈旧引用（#7）

四种复用型会话（计划 / 日报周报 / 点子关联 / 点子头脑风暴）在登记或引用的会话**已经不可用**时，
点下去**没有任何反应**，而且那行陈旧引用**永远不会更新** —— 该链路从此再也开不出会话。

根因是客户端**拿着存下来的 `session_id` 直接切会话，不验证可用性**：

1. DSH 的「归档会话」只把 id 收进工作区归档集（**连文件都不删**），所以归档会话仍在会话列表里、
   `sessions.open()` 不抛错；但宿主随后 `clearArchivedCurrent()` 把选中清掉 —— 用户看到的是**静默无反应**；
2. 会话被**物理删除**时 `open()` 直接抛 `sessions.select: unknown session …`；
3. 登记行 / 报告行**只在新建成功之后**才写 → 陈旧引用永不更新 → 死锁。

**修法**：新增纯判据 `src/client/aiSessionReuse.ts#isAiSessionReusable()`：

| 判据 | 结论 |
|---|---|
| 宿主归档集含该 id | **不可复用** |
| 会话列表 `phase === 'ready'` 且 `ids` / `current` 都查不到 | **不可复用**（物理删除） |
| 列表 `pending`（启动瞬间）或旧宿主缺这两份快照 | **不下结论**（零回归，保持原行为） |

判据不成立时**落回新建**（登记接口是 upsert，会自动覆盖陈旧那行，链路自愈）或**明确提示**。
覆盖**五处**裸切：登记表复用、**报告行自己的 `sessionId` 回退（第二条独立路径）**、
「进入复盘会话」、任务详情「会话」页签行、草案横幅「回到关联 / 头脑风暴会话」。

> 原作者那条"列表 `pending` 时不下结论"的取舍写得特别好：比直接 `!ids.includes(id)` 稳得多 ——
> 启动瞬间不会凭空多开一个会话。这条我们没动。

## 5. 破坏性变更

**无接口破坏。** 行为变更一处：`isTargetConfigured` 在"没绑过投递目标"时返回 `false`
（即恢复"不尝试投递"的既有语义，而不是 PR 原稿的乐观放行）。

数据层：`SCHEMA_VERSION` 仍为 **18**，本版未加迁移。

## 6. 依赖与支持边界

与 v1.15.2 相同，无变化。最小支持 DSH `0.1.5-rc.1`（Web）；`inject` 仍精确 5 项
（`sessions` / `workspaces` / `connection` / `slots` / `layout`），`commands` 为服务端前置条件。

## 7. 验收方式

```powershell
pnpm typecheck                                   # 0
pnpm test                                        # 534 pass / 0 fail（上一版 521）
node scripts/repro/probe-capacity-mutations.mjs  # 19/19 全红（未退化）
node test/reminderWiring.test.mjs                # 3/3（本版新增的源码级不变量）
node --test test/aiSessionReuse.test.mjs         # 10/10（PR #8 带来的纯判据单测）
node scripts/repro/harness-real-browser.mjs --case all   # 51/51
node scripts/check-installed-version.mjs
node scripts/check-installed-fingerprint.mjs
```

界面逐条（重启 `dsh web` + 浏览器硬刷新后）：

1. 让 AI 拆一条带子任务的草稿 → 确认后**子任务也有提醒**了（改前必为 0）；
2. 重启 `dsh web` → 打开设置页「微信提醒」→ 已绑定的目标应**第一次就显示已配置**（改前必为"未配置"）；
3. 重启后等到期提醒 → **能发出来**（改前会被静默跳过，直到手动保存一次设置页）；
4. 给某任务编一个已归档的头脑风暴会话 → 再点「AI 头脑风暴」→ 应**新建**一个会话、登记行被覆盖
   （改前点了没反应且永不自愈）；
5. 任务详情「会话」页签里点一条已归档/已删除的会话 → 应给**明确提示**，不再静默。

- 三项修复的**真机点测由原作者完成**（其 Issue/PR 里附了实测记录）；本版只做本机门禁与源码级复核，

  `PATCH` 会把默认提醒补回去。站在"补上缺失的提醒"角度合理，站在"尊重显式删除"角度可能需要标记位。
