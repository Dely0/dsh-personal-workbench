# v1.15.7 Release Notes

> 主题：**客户端两处 P0** —— ① 快速录入因为「模型选择接口」被**死锁**（选过模型就再也用不了快速录入，
> 而且界面内**改不回默认模型**，只能手改浏览器 localStorage）；② DSH `0.1.7-rc.2` 客户端上
> **系统通知失败被完全吞掉**（"授权显示已开启，点发送测试通知毫无反应"且无任何可读信息）。
>
> 两处都按「**不得静默**」修：拿不到模型目录时**降级跟随默认模型并说清原因**，
> 系统通知的**请求与发送都变成可观测**。
>
> 上一个稳定点：`v1.15.6`

宿主侧的判据来自**读桌面端自身的客户端 bundle**（`resources/app.asar` 内层 `dsh/` 里的
`@deepseek-ai/dsh-client-ui-model-selection@0.1.7-rc.2`），不靠猜：

  `dsh.profile.bundles` 里）—— 所以旧报错文案「当前 DSH 未提供模型选择接口，请升级 DSH」

本版还跑了**一轮独立审查**（空上下文子 agent，`fresh-eyes-review`）：它报了 2 条，
**都确认成立并已修**（见 §3）。这两条都是"同一个事实被独立计算多次"这一类 ——
第一版修复只覆盖了菜单那条路径，门禁与提交路径的**成因措辞**没有一起收敛。

## 1. 主题一：快速录入的模型选择**死锁**（P0，阻断性）

### 现象

用户曾在快速录入的模型选择器里选过模型（选择被持久化到
`localStorage['dsh-personal-workbench.quickModelSelection']`），此后：

| 路径 | 用户看到 |
|---|---|
| 提交快速录入 | `当前 DSH 未提供模型选择接口（modelDirectories），无法为快速录入切换模型。请升级 DSH 或改回"跟随 DSH 默认模型"。` —— **整条快速录入中断** |
| 点模型下拉框想改回默认 | 菜单**打不开**（被门禁拦下） |

而**唯一的写入口只有那个菜单** ⇒ **界面内没有任何办法改回默认模型**，只能手改浏览器存储。
即"一个可选增强（另一个客户端插件提供的下拉框）把整条快速录入拖死"。

### 原因（两层，必须分开说 —— 这正是旧文案把排查带偏的地方）

`resolveModelDirectory()` 的旧写法是 `try { … } catch { return undefined }`，
把两件**完全不同**的事实压成同一个 `undefined`：

1. **服务不在场**（`ctx.get('modelDirectories')` 拿不到，或没有 `directoryFor`）；
2. **服务在场，但这个会话取不到目录** —— 宿主的 `directoryFor(sessionId)` 抛
   `resolved no binding`（本次实测到的就是这一类）。

两种情况在界面上被说成同一句"当前 DSH 未提供模型选择接口"，而本机 provider 是装着的。

### 修法

1. **解析收敛成一处纯判定**：新增
   `modelCapability.ts#resolveModelDirectoryOutcome(readService, sessionId)`，
   返回 `{ok:true, directory}` 或 `{ok:false, code:'service'|'session', detail}`，
   **绝不返回裸 `undefined`**（`readService` 自身抛错也被包住并归类）。
   成因措辞由 `modelDirectoryUnavailableReason(outcome)` **唯一**产出。
2. **提交路径不再抛错（口径 A：自动降级）**：`selectionToApply(selection, outcome)` 决定
   "这次到底换不换模型" —— 拿不到目录就**忽略已有选择、按「跟随 DSH 默认模型」跑完**，
   并给一条明确说明"本次未切换模型 + 真实原因"的提示（控制台同时留痕）。
   **既有设计意图保留**：拿到目录时照旧应用用户所选模型，且 `directory.select()` 的真实失败
   **仍然原样上抛**（不静默）。
3. **界面保留出口（口径 B）**：`gateModelPicker` 的判据加上"菜单里是否还有清空出口"
   （由 `modelMenuMode()` 唯一判定）—— 有残留选择时菜单**照常开得起来**，退化成
   **只列一项**「跟随 DSH 默认模型」+ 一条原因说明；清空走 `onChange(null)` +
   `localStorage.removeItem`，**不依赖任何模型目录**。
4. **解析时机不再永久化**：`openPicker()` 每次点击**重新解析**一次
   （宿主的服务/会话可能晚于组件首次渲染就绪）。原实现把解析结果按
   `[runtime, directorySessionId]` 缓存，"一次失败即永久不可用"因此消失。
   ⚠️ 诚实边界：`useMemo` 缓存/时机这条**假设并未被证实**（无法在本机驱动浏览器取证），
   所以这里**只加了幂等的显式重试**，没有改成定时轮询或状态写入。

## 2. 主题二：rc.2 上系统通知**失败不可观测**（P0）

### 现象

设置里通知显示「授权显示已开启」，点「发送测试通知」**看不到任何系统通知**，
而且**没有任何可观测的信号**（界面无提示、控制台无日志）。

### 原因（三处结构性问题）

| 位置（改前） | 问题 |
|---|---|
| 发送测试通知 | `new Notification(...)` 外层是空 `catch` —— 失败被**完全吞掉** |
| 请求授权 | 直接调 `Notification.requestPermission()`，**没有先判 `typeof Notification === 'undefined'`**（初始化时判了、请求路径漏了）⇒ 不支持的客户端上抛 `TypeError`，且没有 `.catch()` ⇒ 用户点完什么也看不到 |
| 设置面板 | 只有 `granted` 才渲染「发送测试通知」，也不交代"已授权 ≠ 一定能弹出来" |

### 修法

新增纯模块 **`src/client/notificationCapability.ts`** 作为唯一实现：

- `readNotificationCtor(source)`：从任意"全局对象形状"读构造函数（读不到 = **不支持**，
  **绝不回落到 `globalThis`** —— 回落会把"宿主没提供"误判成"权限是 default，去请求吧"）；
- `classifyNotificationPermission(ctor)`：**四态**
  `unsupported` / `default`（可请求）/ `denied` / `granted`；
- `notificationStateText(state)`：四态的界面文案（**唯一实现**，
  `denied` 给"去浏览器站点权限改回允许"，`granted` 明确交代
  **系统级仍可能丢弃**：Windows「通知和操作」总开关、专注助手/勿扰、按应用单关、横幅被关 ——
  这一层**网页读不到也管不了**）；
- `requestNotificationPermission(ctor)`：不支持/没有 `requestPermission` **当场失败并说清原因**；
- `sendSystemNotification({...})`：失败**返回原因 + 落一条控制台日志**，不再静默。

设置面板按四态渲染对应操作与文案；到期提醒的发送路径同样改走它
（后台流程失败只记日志、不弹错误打扰用户，但**不再是不可见的**）。

> ⚠️ 一条必须说清的边界：`Notification.permission === 'granted'` 只覆盖**浏览器站点权限**这一层。
> 系统通知仍可能被**操作系统**静默丢弃。所以"已授权"的文案里把这件事写出来了，
> 且成功回执只说"已交给浏览器"，**不说"已显示"**。

## 3. 独立审查发现并修掉的两条（v1.15.7 开发期内）

| 编号 | 结论 | 处理 |
|---|---|---|
| F1（高） | 第一版只修了菜单那条路径：`gateModelPicker` 只吃 `hasDirectory: boolean`，于是"服务在场、只是这个会话取不到目录"仍然被说成「当前 DSH 未提供模型选择接口」—— **同一个事实两处翻译、措辞互相矛盾**，且提示让用户"去菜单里改回默认模型"而此刻菜单正是被门禁挡住的 | 门禁入参改为 `unavailableReason`（由 `modelDirectoryUnavailableReason()` 唯一产出、**原样透传**）+ `recoverable`（由 `modelMenuMode()` 唯一判定）；降级提示改为 `QUICK_MODEL_DEGRADE_PREFIX` + 真实成因，且"可以在这里改回"只在出口真的可达时才给 |
| F2（低） | 降级菜单的"原因"被算了两遍，且多存了一个**只写不读**的 state（渲染读的是 `menuDecision.reason`）；出口可达性同样有两处独立计算 | 删掉该 state；`recoverable` 不再由门禁自己看选择状态，改由菜单判定的结果传入 |

两条修完后，独立审查给出的缺陷探针由 `exit 1` 转为 `exit 0`（判定式一字未动，
只同步了入参形状）。原始证据留在本机 `.review-evidence/`（不入库）。

## 5. 依赖与支持边界

- **没有新增 DSH 服务依赖**：`dsh.client.inject` 仍是空数组，`modelDirectories` 继续走
  `ctx.get` 软探测（`test/capabilities.test.mjs` 把 inject 精确锁成 5 项）。
  即：**没装 `dsh-client-ui-model-selection` 的机器照样能用**，只是少一个下拉框。
- **数据库 schema 未变**（仍是 18）⇒ 本版对数据库**没有前进**，从本版回退到 `v1.15.6` 不会
  让宿主拒绝启动。
- DSH 最低支持版本不变（`0.1.5-rc.1`）。

## 6. 验收方式（用户已在本机实测确认）

1. 设置 → 通知 → 点「**发送测试通知**」：应能看到系统通知；若环境确实不支持或被系统拦下，
   **界面上必须给出可读原因**（不再"显示已开启却毫无反应"）。
2. 快速录入：若出现过模型目录拿不到的情况，应看到明确提示
   "本次未切换模型，已按「跟随 DSH 默认模型」继续" + **真实原因**；
   内容也能**照常提交**，不再中断。
3. 快速录入选模型的下拉框里选择「跟随 DSH 默认模型」后，
   `localStorage['dsh-personal-workbench.quickModelSelection']` 应被清除（无需手改浏览器存储）。
4. 浏览器控制台不应再出现被吞掉的静默失败；模型目录不可用时有一条
   `[workbench] 模型目录不可用（service|session）：…` 的可读警告。

> 本版发布时，本机 profile 依赖的是**带构建戳的开发包**
> （`_local-build/dsh-personal-workbench-dev-73e1503-20260928-165116.tgz`），
> 其 `lib/` 与本次 npm 产物**逐文件一致**（`scripts/check-installed-fingerprint.mjs` 退出码 0）。
> 也就是说：本机 profile 声明的版本号仍是 `1.15.6`，但**内容是本版**。
> 若要让它改回按 npm 版本消费，把 profile 依赖切到 `1.15.7` 并重启即可（重启由用户发起）。

## 7. 已知问题 / 未覆盖

- **本机 `desktop` profile 里本插件仍是 `1.15.6`**（本版只在 `web` profile 装盘验证），
  未同步装盘属于已知的本地环境状态，不是本版缺陷。
- **"已授权但系统通知仍不弹"的 OS 侧成因无法由网页判定**（Windows 通知总开关、专注助手、
  按应用单关）。本版能保证的是：**这层信息会写进界面文案、失败会给出可读原因**。
- 关于"宿主 `modelDirectories` 服务注册晚于组件首次渲染"这一条，只做了**幂等重试**兜底，
  **未取证**（无法在本机驱动浏览器）；如果将来能拿到实证，可进一步简化为依赖变化驱动。
